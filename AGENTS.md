# Benchmark — протокол для модели-участницы

> Этот файл читает LLM-модель, которая выполняет задачу бенчмарка
> в роли **участника** (слот modelA или modelB).

## Что делать

1. **Прочитай задачу** — `data/tasks/T-NNN-<slug>/task.md`. Изучи: front matter,
   описание, источники требований, критерии, формат ответа и ограничения.
   Явно указанный task-id имеет приоритет. Без него используй `current_task`
   из `data/settings.yaml`; если текущая задача не задана — последнюю созданную.
   Если заданной текущей задачи нет, сообщи об ошибке, не подменяй её другой.

2. **Подготовь baseline без изменения рабочего проекта.** Зафиксируй его
   `git status --short` и `git rev-parse HEAD`. Если есть `baseline_commit`,
   анализируй именно этот коммит, а не текущую версию или незакоммиченные правки.
   Для checkout и любых разрешённых задачей экспериментов используй новую
   отдельную копию, созданную через `git clone --no-local --no-checkout`.
   Checkout baseline выполняется только внутри копии. Проверяй её полный HEAD.
   Рекомендуемый путь: `.devin/cache/benchmark/<task-id>/<slot>-<unique-run>`
   внутри Benchmark; область `.devin/cache/` игнорируется Git.
   Если файловый инструмент блокирует игнорируемый каталог, запроси явный доступ
   только к своему каталогу копии. Разрешение scope может не отменять ignore:
   если блокировка сохраняется, согласуй отдельный каталог вне Benchmark.
   Не меняй `.gitignore` или политики доступа ради обхода ограничения.
   Не используй общую копию между A, B и судьёй. Не переноси `.env`, `.dev.vars`,
   реальные секреты, runtime-state, логи и пользовательские данные.
   Если проект можно только читать, разрешён анализ Git-объектов baseline без
   checkout; недоступность безопасной копии не разрешает менять оригинал.

3. **Изучи код проекта** согласно задаче. Не запускай приложение, не выполняй
   deploy, remote migrations и действия с реальными пользователями.
   Тесты и экспериментальные патчи разрешены только если это допускает задача,
   только в своей копии и с синтетическими данными/локальными подменами.
   Проверяй отсутствие внешних обращений: отдельный каталог не изолирует сеть.
   Сначала воспроизведение на baseline, затем проверка предлагаемого исправления.
   Недоступные проверки отмечай явно; не выдавай код теста за выполненный запуск.

4. **Напиши ответ** — MD-файл своего слота:
   ```
   data/answers/<task-id>/modelA.md   # если ты участник A (@benchmark-run-a)
   data/answers/<task-id>/modelB.md   # если ты участник B (@benchmark-run-b)
   ```
   Ручной прогон произвольной модели из реестра — файл
   `data/answers/<task-id>/<model-id>.md` по формату `data/answers/_TEMPLATE.md`.
   Формат и рубрика конкретной задачи имеют приоритет над общим шаблоном ниже.

## Формат ответа

````markdown
---
task: T-NNN
model: modelA
date: YYYY-MM-DD
---

# Ответ на задачу T-NNN

## Анализ
<!-- Краткий обзор: что рассмотрено -->

## Находки
### 1. [Название]
**Файл:** `path/to/file.kt:NN`
**Критичность:** критичный / средний / низкий
**Описание:** ...

**Пример:**
<!-- Входные данные, на которых баг проявляется -->

**Исправление:**
```kotlin
// Исправленный код
```

## Граничные случаи (проверено, не баг)
<!-- Что проверено и почему работает корректно -->

## Дополнительные находки
<!-- Неиспользуемые импорты, стиль и т.д. -->
````

## Правила

- **Ответ = MD-файл** (анализ + код в блоках), не код в рабочем проекте.
- **Максимально полный и проверяемый ответ** — все установленные причины и
  граничные случаи. Не придумывай баги ради количества; гипотезы отделяй от фактов.
- **Код в блоках** `kotlin`, `go`, `typescript`, `tsx`, `sql` или `diff` по задаче —
  судья оценивает качество исправлений и проверок, не только описание.
- **UI-тексты и ответ на русском**, код и идентификаторы на английском.
- **Независимость:** отдельные новые чаты для A, B и судьи. Во время анализа
  не читай другие/прежние ответы, вердикты, ELO, реестр моделей и чужие копии.
  Соблюдай ограничения задачи на готовые аудиты и историю исправлений.
- **Не модифицируй исходный проект.** Никаких checkout/reset/clean/stash,
  перезапуска процессов, сборки рабочих exe или операций с продакшеном в нём.
  В конце сравни HEAD и статус с началом; не удаляй чужие изменения, даже если
  они появились за время анализа. Не выполняй автоматическую очистку проекта.
- **Сохрани ответ** в файл своего слота; при повторном прогоне он перезаписывается.
  Если инструмент требует предварительно прочитать существующий файл, сначала
  зафиксируй полный новый ответ в своей копии; затем прочитай только файл своего
  слота для технической перезаписи и запиши этот текст без изменений по старому
  ответу. Не используй старый ответ для дополнения нового и не читай чужой слот.
- **Свежесть пары подтверждает координатор:** наличие двух MD и совпадение дат
  не доказывает, что оба получены для текущего сравнения. Не суди собственный ответ.
- **Собственная рубрика задачи:** если `task.md` задаёт свой формат и шкалу
  оценки, применяются они; задача без собственной рубрики оценивается по
  прежней схеме /50.

## Саморегистрация

Если ты делаешь ручной прогон под своим `<model-id>`, а тебя нет в `data/models.yaml`,
зарегистрируйся заранее:
```
python tools/register_model.py --auto --id <slug> --name "<Имя Модели>"
```
Для skill-прогонов A/B регистрация не требуется — участник не знает реальный `id`.
Координатор укажет реальные `id` при записи вердикта. Правило анонимности относится
к A/B; при ручной саморегистрации реестр читается только для регистрации, не оценки.

## Проверка самого Benchmark (не прогон участника)

- `uv run python tools/test_elo.py` — тесты ELO, регистрации и выбора задач.
- `uv run python tools/elo.py --check` — проверка индекса и журнала без записи.
- `tools/test_pairing.py` при запуске целиком временно переписывает реальные
  `data/models.yaml` и `data/index.json`. Не запускай его целиком в рабочем
  репозитории с текущими сравнениями; используй отдельную копию. Проверку
  `test_rematch_recommendations()` можно вызвать отдельно: она подменяет
  статистику в памяти и не вызывает сценарий архивации моделей.

## Git — коммиты (для работы над этим репозиторием)

- `git commit` / `git push` — **только по явному указанию** пользователя
  («закоммить», «запушь», «commit and push»). Не коммитить «заодно».
- **ЗАПРЕЩЕНО** добавлять в сообщение коммита трейлеры `Generated with ...`,
  `Co-Authored-By:` и любые другие авторские/агентские пометки.
- Сообщение — через файл: `git commit -F <file>` (PowerShell не поддерживает
  heredoc `$(cat <<'EOF'...)`). Файл писать без BOM
  (`[IO.File]::WriteAllText` с `UTF8Encoding($false)`).
- Перед коммитом проверь текст: никаких строк, начинающихся с
  `Generated with` или `Co-Authored-By:`.
- Полные правила — `.devin/rules/git.md`.

## Версии и changelog (обязательно)

- Версия проекта меняется **только в момент релиза**: бамп вне релиза запрещён,
  между релизами номер остаётся номером последнего релиза. У статического трека
  версия заморожена и не меняется вовсе.
- В changelog попадают **только глобальные доработки** — новая функция, заметное
  изменение поведения, фикс, который пользователь реально видит. Пункт пишется
  в секцию `## [Unreleased]` в момент работы, а не перед релизом. Мелочь
  (косметика UI: отступы, цвета, выравнивание, подпись элемента, и локальные
  правки без заметного эффекта), как и чистые доки, спеки, тесты, CI,
  внутренний рефактор, в changelog не пишется.
- Релиз (где есть конвейер): `release.ps1 -Prepare` → сборка артефактов в `dist/`
  → `release.ps1`. Порядок не меняется.
- Секция changelog начинается с **пользовательского саммари** — 2–5 строк о том,
  что изменится для пользователя, — **выше первой строки** `###`; под категориями
  (`### Добавлено`, `### Исправлено` и аналоги) идут инженерские детали: change-id,
  состав изменений, тесты, метрики. Подготовка релиза откажет, если саммари нет.
- Заметки GitHub-Release берутся из этого блока автоматически — отдельное
  описание релиза писать не нужно и нельзя дублировать.
- Сверка перед работой и после: `python scripts/check-version.py`
  (exit 0 — версия и changelog согласованы, exit 1 — рассинхрон).
- Полные правила и запреты: `docs/versioning.md`.
