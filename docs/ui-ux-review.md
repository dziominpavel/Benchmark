# UI/UX-обзор консоли: находки и предложения

**Дата:** 2026-10-17
**Охват:** локальная консоль координатора (`tools/server.py`, `http://127.0.0.1:5000`) — «Рейтинг», «История», «Аналитика», «Настройки», профиль модели, добавление/редактирование моделей и тасок. Публичная витрина `web/` в обзор не входит.
**Метод:** разбор кода и HTML-рендеров страниц в режиме read-only; файлы и данные проекта не изменялись.
**Срез данных:** 33 модели, 535 вердиктов, 1 активный таск (T-001), покрытие пар 528/528.

Кратко: консоль зрелая — единая дизайн-система, живые тренды, объясняемые рекомендации, богатый профиль модели, журнал с поддержкой аннулирования (tombstone). Основные пробелы: исправление вердикта доступно только из CLI; после записи форма теряет контекст; история не умеет искать по таску/датам/исходу и не масштабируется по пагинации; «Аналитика» — одна карточка; селекты моделей не рассчитаны на 1000 моделей. Ниже — предложения по убыванию полезности; «эффект» и «трудоёмкость» — экспертные прикидки, не сроки.

## Что уже работает хорошо

- Цельная дизайн-система (`tools/static/css/console.css`): тёмная/светлая темы, адаптив (контрольные точки 900/639 px), аккуратные пустые состояния, aria-атрибуты.
- Главная: тренд-бейджи за 5 личных игр с тултипами («5 личных игр · ΔELO +32 · место 7→6»), легенда методики (K, ничья, «±», прогрев), фильтры по активности/агенту/компании.
- Карточка рекомендаций объясняет выбор пары (счёт личных встреч, ΔELO, пометка «доп. точность: рематч») и умеет подставлять пару в форму кнопкой «Прогнать».
- Профиль модели: стат-карточки, «Динамика ELO» (SVG), полная таблица «Личные встречи», «История матчей» (соперник/дата/исход/Δ).
- Журнал append-only с tombstone-механикой (`void_of`): реплей и индекс уже исключают аннулированные (`tools/elo.py`, `void_matchup`). Для отмены из UI не хватает только самого UI.
- Кэш тяжёлых агрегатов (`tools/data_cache.py`) — новые аналитические блоки можно добавлять дёшево.

## 1. Аннулирование вердикта из консоли

**Сейчас.** Отмена — только из CLI: `python tools/record_verdict.py --void T-001/001 --reason "…"` (`tools/record_verdict.py:57`, `tools/elo.py:427` — `void_matchup`). Журнал получает tombstone-событие (`void_of`), реплей исключает аннулированный матч. В консоли нет ни кнопки, ни статуса: после аннулирования вердикт просто исчезает из рейтинга, аудит-след остаётся только в файле журнала.

**Почему это важно.** Ошибка («не та модель», «не тот победитель», дубль) исправляется там же, где обнаруживается — в истории; сейчас для этого нужно помнить CLI и выполнять команду в терминале. Чем больше вердиктов, тем дороже ошибка.

**Что сделать.**
- POST-роут (например, `/verdict/void`) с полями `matchup_id` и `reason`: проверка формата `T-NNN/NNN`, подтверждение, вызов `void_matchup`, редирект с success-сообщением.
- Кнопка «Аннулировать» — в строке истории (когда у вердикта есть `matchup_id`) и в списке вердиктов таска (п. 7).
- Ссылка «Отменить» — прямо в success-строке после записи вердикта: самая частая ошибка обнаруживается сразу. Потребуется прокинуть `matchup_id` в редирект (сейчас success-текст несёт только пару и исход, `tools/server.py:2412`).
- Статус аннулирования — показывать: перечёркнутая строка с пометкой и причиной плюс фильтр «показать аннулированные», чтобы было видно: запись не потеряна, а именно аннулирована.

**Где менять.** `tools/server.py` (роут рядом с `record_verdict_route`, 2378; шаблон истории ~1100), `tools/elo.py` (`void_matchup`, 427). Формат журнала менять не нужно.

**Эффект / трудоёмкость.** Высокий / низкая–средняя. Закрывает цикл «запись → проверка → исправление», который сейчас разорван между браузером и терминалом.

## 2. Форма вердикта: сохранять контекст, добавить дату

**Сейчас.** Форма живёт на главной: «Модель A», «Модель B», «Таск», три кнопки исхода. После отправки `record_verdict_route` (`tools/server.py:2378`) делает `redirect` на главную с текстом «Записано: A vs B → победила A» — но выбор моделей сброшен (таск подставляется текущий: `pre_task or current_task`, `tools/server.py:1017`). Даты в форме нет: журнал всегда пишет сегодняшнюю дату (`tools/elo.py:412`, `date.today()`); в CLI параметра `--date` тоже нет.

**Почему это важно.** Вердикты пишутся сериями (в журнале видны батчи записей подряд). Каждая запись — это заново два выпадающих списка; если ошибся, форма уже перезагружена. Задним числом внести вчерашние матчи корректной датой тоже нельзя.

**Что сделать.**
- Не перезагружать форму после записи: показывать success на месте и сохранять выбранный таск (и, как минимум, модель-победителя в поле A — следующая пара часто с её участием).
- В success-строке — «Отменить» (п. 1) и «Записать ещё».
- Кнопка «поменять A ↔ B» — частая ошибка при выборе из списка.
- Поле «Дата» (по умолчанию — сегодня): потребуется параметр `date` у `record_verdict` (сейчас жёстко `date.today()`), опционально `--date` в CLI.
- Под селектами показывать счёт личных встреч выбранной пары — чтобы сразу понимать, первая это встреча или рематч (данные уже есть: `get_pair_stats`, `tools/server.py:122`).

**Где менять.** `tools/server.py` (2378–2414, шаблон формы ~840–1070), `tools/elo.py` (`record_verdict`, 337), при желании `tools/record_verdict.py`.

**Эффект / трудоёмкость.** Высокий (самый частый сценарий) / низкая–средняя.

## 3. История: фильтры, метки, пагинация

**Сейчас.** `/history` (`tools/server.py:1856`) отдаёт 20 записей на страницу (`page_size = 20`, 1936–1947). Фильтры страницы: модель (select), агент, компания, режим «скрывать/подсвечивать». Строка (`format_elo_history`, `tools/render_helpers.py:158`): модели A и B с подписью «провайдер · агент», ELO до → после и Δ для каждой, дата-время. Чего нет: таска (в рендере нет ни одного `T-0…`), метки исхода (победитель вычисляется только по Δ), ссылок на модели и `matchup_id`. Пагинация — полный список номеров (шаблон 1109–1112): сейчас 27 ссылок подряд; при 10 000 вердиктов это 500 ссылок.

**Почему это важно.** Найти «вердикт такой-то пары по такому-то таску за прошлую неделю» нельзя — только листать по 20. Таск при этом — первичная сущность бенчмарка. Строки не кликабельны, хотя все остальные списки консоли ссылаются на модели.

**Что сделать.**
- Фильтры: таск, диапазон дат (или пресеты «7/30/всё»), исход (A / B / ничья), «только аннулированные» (после п. 1), поиск по паре.
- Все фильтры — в URL (частично уже так: `?model=…&page=…`): удобно для закладок и кросс-ссылок из профиля модели и страницы таска.
- Строка: бейдж таска, явная метка «победила A/B/ничья», ссылки на модели, `matchup_id` (якорь для аннулирования и внешних ссылок).
- Пагинация: поле «страница №», окно номеров вокруг текущей (`1 … 12 13 14 … 27`), кнопки «‹ / ›», «в конец»; при включённых фильтрах подписывать «найдено N».
- Опционально: «показать ещё» для быстрых долистываний.

**Где менять.** `tools/server.py` (1856–1970 — сборка списка и пагинация; шаблон ~1100), `tools/render_helpers.py` (`format_elo_history`, 158), `console.css` (бейджи).

**Эффект / трудоёмкость.** Высокий / средняя.

## 4. Аналитика: от одной карточки к дашборду

**Сейчас.** `/stats` (`tools/server.py:1999`) — единственная карточка «Распределение Elo» (гистограмма, `build_elo_distribution_svg`, `tools/render_helpers.py:379`) со сводкой «моделей: 33 · ниже 1200: 17 · выше/равно 1200: 16 · среднее: 1199» и панелью фильтров. Спека `leaderboard-ui` предусматривает блочную структуру («в первой итерации одна карточка») — страница задумана как место для роста.

**Почему это важно.** Данные для содержательной аналитики уже есть: 535 вердиктов в журнале и `elo_history` с точкой на каждый матч (дата, ELO до/после, Δ). Сейчас страница отвечает на вопрос «какой разброс рейтингов», но не на «кто вырос за месяц», «как распределены игры», «какие пары не сыграны», «какие агенты сильнее».

**Что добавить (по убыванию полезности).**
1. **Динамика ELO во времени** — мультилиния с выбором моделей (топ-N или чекбоксы) и периода (30/90/всё): переиспользовать `build_elo_svg` (`tools/render_helpers.py:227`), который уже рисует такое на странице модели.
2. **Активность по дням** — столбиковая диаграмма «вердиктов в день» (из `recorded_at`): видно темп прогонов и паузы.
3. **Покрытие пар** — «сыграно X из 528 (C(33,2))» с разбивкой по таскам: для T-001 значение уже считается (`memo_coverage`, `tools/server.py:404`).
4. **Хитмап «модель × модель»** — число игр (или винрейт) по парам: сразу видны «дырки» покрытия; клик по ячейке → личные встречи.
5. **Агрегаты по агентам и компаниям** — число моделей, средний/медианный ELO, суммарные игры, винрейт: сводка «какой агент/провайдер» сильнее без чтения таблиц.
6. **Взлёты и падения** — топ ΔELO за 7/30 дней и «остывшие» модели (давно без игр): план следующих прогонов.
7. **Неопределённость рейтинга** — пометка «мало игр» (<10, в легенде уже есть «прогрев») и/или интервал «±400/√игр» (`confidence_half_width` / `format_confidence`, `tools/render_helpers.py:500,516`), чтобы не переоценивать модель с тремя играми.

**Где менять.** `tools/server.py` (`stats_page`, 1999 + шаблон), `tools/render_helpers.py` (новые SVG-хелперы в том же стиле: bar-chart, heatmap), `tools/data_cache.py` (готовый кэш, `cached`, 98), `console.css`.

**Эффект / трудоёмкость.** Высокий / средняя–высокая; удобно наращивать по одному блоку.

## 5. Рейтинг и селекты: поиск, сортировка, автодополнение

**Сейчас.** На главной есть фильтры (активность/агент/компания/режим), модели в таблице — ссылки на профиль. Но: нет текстового поиска по имени/id; заголовки таблицы не сортируются (порядок жёстко «по месту»); все выборы моделей — обычные `<select>`: форма вердикта (два списка по 33 пункта), фильтр истории, настройки. Проект целенаправленно масштабируется к 1000 моделям (`scale-console-1000-models`) — списки `<option>` станут первым, что сломает юзабилити.

**Что сделать.**
- Поиск по имени/id над таблицей, в связке с фильтрами.
- Сортировка по клику на заголовок: место/ELO/игры/винрейт/тренд; индикатор стрелки, `aria-sort`, состояние в URL.
- Автодополнение в селектах: быстрый вариант — `<input list="…">`/datalist по name+id; аккуратный — фильтруемый комбобокс с группировкой (агент → модели).
- Запоминать выбранные фильтры (URL уже несёт параметры; можно продублировать в localStorage).

**Где менять.** `tools/server.py` (`leaderboard` 2075, `filter_panel_context` 303, шаблоны), `console.css`.

**Эффект / трудоёмкость.** Средний–высокий (растёт с масштабом) / средняя.

## 6. Профиль модели: место, таски, метаданные

**Сейчас.** `/model/<id>` (`tools/server.py:1973`) показывает: шапку (имя, «провайдер · агент», ELO, «Изменить»), стат-карточки (матчи/победы/поражения/ничьи/винрейт), «Динамику ELO», «Личные встречи» (таблица по всем соперникам), «Историю матчей» (соперник/дата/исход/ELO до/Δ/после). Не показаны: место в рейтинге и тренд; в каких тасках модель играла; метаданные реестра, которые уже заполнены в `data/models.yaml` (`version`, `released`, `added`, `status`, `notes`); строки «Истории матчей» никуда не ведут.

**Что сделать.**
- Карточка «Место в рейтинге» (+ стрелка тренда из `compute_rank_trends`, `tools/render_helpers.py:561`) и «Последний матч».
- Блок «Покрытие по таскам»: по каждому активному таску — сколько матчей (и был ли таск вообще).
- Метаданные: версия/релиз/дата добавления/статус/заметки из реестра.
- «История матчей»: ссылка на строку истории/вердикт (после п. 3) + кнопка «Показать в истории» (отфильтрованная по модели история возможна уже сейчас).
- Опционально: селект «Сравнить с…» над «Личными встречами».

**Где менять.** `tools/server.py` (`model_page`, 1973), `tools/render_helpers.py` (`get_model_detail`, 42), шаблон + `console.css`.

**Эффект / трудоёмкость.** Средний / средняя.

## 7. Страница задачи

**Сейчас.** Таск — полноценная сущность: `data/tasks/T-NNN-<slug>/task.md`, консоль умеет создавать/редактировать/переключать (`add_task` 2975, `edit_task` 3005, `/task/<id>/toggle` 3040, `/task/<id>/current` 3051; раздел «Таски» в настройках), в каждом вердикте журнала есть поле `task`. Но страницы задачи нет; в истории таск не отображается; отдельного счётчика «сколько сыграно по таску» тоже нет.

**Что сделать.** Страница `/task/<id>`:
- шапка: название, проект, baseline-commit, статус, признак «текущая», ссылка на `task.md`;
- прогресс: вердиктов по таску, покрытие пар, число уникальных моделей, число аннулированных (после п. 1);
- список вердиктов таска — тем же рендером, что история (п. 3);
- кнопка «Записать вердикт по таску» → форма с предвыбранным таском: механика уже есть, `/?task=T-NNN` (`tools/server.py:2161`);
- ссылки: из «Настроек» (раздел «Таски»), из бейджей таска в истории (п. 3), из рекомендаций.

**Где менять.** `tools/server.py` (новый роут рядом с 1973/3005; ссылки в шаблонах), `console.css`.

**Эффект / трудоёмкость.** Средний / средняя. Станет заметнее с ростом числа тасков.

## 8. Очередь рекомендаций: противоречие и объяснение

**Сейчас.** В настройках карточка «Очередь рекомендаций (0)»: «осталось 0 · закрыто 528 из 528», подсказка «порядок совпадает с кнопкой „Прогнать“ на главной», блок «Очередь пуста — открытых пар нет» — и сразу под ним строка очереди с парой и пометкой «рематч». Это фолбэк «доп. точности» из `get_recommendations` (`tools/server.py:629`), но выглядит как баг. На главной та же пара подана богаче: «личные встречи: 1 · счёт 0:1», «счёт 0:1 · Δ=2», «доп. точность: рематч», «таск: T-001».

**Почему это важно.** Противоречие подрывает доверие к рекомендациям: одновременно «пусто» и «строка есть». Непонятно, почему выбрана именно эта пара и что будет после неё, особенно при нескольких тасках.

**Что сделать.**
- В empty-state писать причину: «Открытых пар нет. Показан матч для доп. точности (рематч)» — или выводить такие строки отдельным подблоком «Доп. точность» вне empty-state.
- В заголовке очереди вместо «(0)» — «открытых: 0 · рематчей: 1».
- Показывать 2–3 варианта (у `get_recommendations` уже есть параметр `top_n`), а не один; на главной — кнопку «другая пара».
- Причину выбора выводить единообразно на обеих страницах (механика есть — `format_reason`, `tools/server.py:817`).

**Где менять.** `tools/server.py` (`get_recommendations` 629, шаблоны главной/настроек, блок очереди 2517–2539), `console.css`.
