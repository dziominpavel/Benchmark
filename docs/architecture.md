# Архитектура ELO Benchmark

## Обзор

Система сравнивает LLM-модели через попарные сравнения (pairwise comparison)
и ELO-рейтинг. Модели отвечают на аналитические задачи, судья сравнивает
два ответа и выбирает победителя, ELO пересчитывается.

## Поток данных

```
① СОЗДАНИЕ ЗАДАЧИ (вручную)
   data/tasks/_TEMPLATE.md → data/tasks/T-NNN-<slug>/task.md

② ПРОГОН МОДЕЛИ (skills)
   @benchmark-run-a T-001 → data/answers/T-001/modelA.md
   @benchmark-run-b T-001 → data/answers/T-001/modelB.md
   (каждый skill сам делает checkout baseline_commit и очистку после;
    участник не записывает свой реальный id)

③ СУДЬЯ
   Путь 1 (skill): @benchmark-judge T-001
     → читает task.md + оба ответа, оценивает 5 критериев (/50)
     → объявляет победителя <a|b|draw>
   Путь 2 (вручную): чат с LLM по docs/judge-prompt.md
     → судья отвечает в чате → координатор переносит итог в веб-форму

④ ЗАПИСЬ ВЕРДИКТА
    Единая точка записи — elo.record_verdict():
    - skill путь:   python tools/record_verdict.py --task T-001 \
                    --model-a <id> --model-b <id> --winner b
    - веб-UI:       localhost:5000 → форма → POST /verdict
                    (task из выпадающего списка активных тасок)
    - CLI вручную:  python tools/record_verdict.py --task T-001 \
                    --model-a <id> --model-b <id> --winner a
     Каждый вызов: seq = max(seq журнала)+1 под файловым локом, recorded_at
     (системное время), ELO-снэпшот (before/after/delta) — одна строка
     data/matchups/journal.jsonl, пересчёт data/index.json.
    Аннулирование: record_verdict.py --void T-001/001 --reason "..."

⑤ LEADERBOARD
    localhost:5000 → таблица ELO + рекомендации + форма вердикта
    История ELO: localhost:5000/history
    Проверка целостности журнала: python tools/elo.py --check
```

## Хранение

**Source of truth (в git, всё под `data/`):**
- `data/models.yaml` — реестр моделей (id, name, agent, provider, version, released, added, status, notes; agent и provider — из справочника, значения вне справочника допустимы и помечаются «вне справочника»)
- `data/lookups.yaml` — справочники агентов и компаний (agents, providers) —
  допустимые значения полей agent/provider; CRUD — секция «Справочники»
  страницы /settings, авто-дополнение — tools/register_model.py
- `data/tasks/T-NNN-<slug>/task.md` — задачи (создание вручную из `data/tasks/_TEMPLATE.md`)
- `data/matchups/journal.jsonl` — журнал вердиктов: единый append-only
  JSONL-файл, строка = событие (поля: version, seq, task, matchup,
  model_a/b, model_a_id/b_id, winner, date, recorded_at, elo-снэпшот;
  tombstone — поле void_of). `seq` — сквозной номер по всему журналу,
  `matchup` — `T-NNN/NNN` (max+1 внутри задачи). Старая раскладка (файлы
  вердиктов по задачам и счётчик seq) упразднена разовой миграцией
  `tools/migrate_journal.py`

**Локально (не в git, игнорируется):**
- `data/answers/T-NNN/modelA.md`, `modelB.md` — транзитные слоты текущего
  судейства; `data/answers/T-NNN/<model-id>.md` — ручные прогоны произвольных
  моделей. Система читает только слоты: для судейства текст копируется в слот.

**Кэш (генерируется, в git):**
- `data/index.json` — ELO + статистика + сводки + история + matchups_digest
  (sha256 содержимого журнала — правка любой строки инвалидирует кэш)

**Генерируется (не в git):**
- Статичных артефактов нет; для просмотра используется веб-UI.

## ELO-движок

- **Начальный ELO:** 1200 для всех моделей
- **Адаптивный K-factor:** <10 игр → 40, 10–30 (включительно) → 32, >30 → 24;
  K применяется индивидуально к каждой модели в паре
- **Пересчёт:** полный реплей `data/matchups/journal.jsonl` в порядке
  возрастания `seq`; события с неизвестными моделями пропускаются молча,
  с неизвестным `winner` — с предупреждением в stderr; аннулированные
  (`void_of`) события игр не создают
- **Снэпшот:** каждый вердикт v2 хранит `elo.{id}.before/after/delta` —
  рейтинги на момент записи. `python tools/elo.py --check` сверяет их
  с реплеем: расхождение = история изменена задним числом
- **Округление:** целое, half-to-even (Python `round`)
- **Подробности:** [elo-mechanics.md](elo-mechanics.md)

## Pairing algorithm

Предлагает следующие пары для сравнения (топ-3, глобально по всем моделям,
без разреза по задачам). Уже сравнённые пары (по событиям журнала, без
tombstone и аннулированных) исключаются.
Ранжирование двухуровневое (`tools/server.py:get_recommendations`):
сначала тир калибровки по `min_games` (0 — новая модель — выше всего,
<3 — калибровка, остальные — ниже), внутри тира — близость ELO:

```
score = closeness = 1 / (1 + elo_diff / 100)   # близкий ELO — информативно
сортировка: (tier ↑, score ↓)
```

Причины в UI — по порогам: 0 игр — «новая модель, ещё не играла»;
<3 игр — «мало игр, нужна калибровка»; Δ<50 — «близкий рейтинг»;
Δ<150 — «различается умеренно»; иначе — «разный уровень — проверить апсет».

Архивные модели исключаются из рекомендаций; наличие ответов пока не
проверяется.

## Веб-сервер

- `GET /` — таблица (`#`, Модель, ELO, Побед, Поражений, Ничьих, Всего),
  статистика, топ-3 рекомендаций,
  форма вердикта (кнопки заблокированы пока A ≠ B не выбраны), последние
  20 записей истории
- `GET /add`, `POST /add_model` — добавление модели по названию (slug генерируется)
- `POST /verdict` — валидация (обе модели из реестра, A ≠ B, task —
  активная таска T-NNN, winner ∈ a/b/draw) → событие в `data/matchups/journal.jsonl` → пересчёт ELO
- Порт: 5000, при занятости — следующий свободный (до 10 попыток)
- `start.bat` — запуск под Windows + открытие `localhost:5000` в браузере

## Статическое зеркало (витрина)

Полный read-only слепок консоли для витрины (`tools/export_web.py`): те же
разделы — рейтинг, история, аналитика, настройки, страницы моделей и очередь
рекомендаций, — но без записи: посетители видят демонстрационную копию и не
могут повредить данные.

```bash
# Сборка с нуля (каталог вывода должен отсутствовать или быть пустым)
uv run python tools/export_web.py --out <каталог> [--catalog-depth 2]
```

- **Режим «только просмотр»** — конфиг `READ_ONLY` в `tools/server.py` и
  контекст шаблонов `read_only()`: плашка «демонстрационная копия — только
  просмотр» со ссылкой в каталог, формы → `<fieldset disabled>`, ссылки на
  запись (`/add`, `/add_task`, `/edit*`) не рендерятся, «Изменить» — нейтральный
  текст, `_load_index()` не сохраняет устаревший `index.json` (пересчёт в памяти).
- **Автономность** — `href|src="/…"` переписываются в относительные файлы
  слепка, маркеры `__catalog__`/`__root__` — по глубине файла (`--catalog-depth`,
  по умолчанию 2 — публикация в `/apps/<slug>/`); внешних запросов нет.
  `?queue_page=K` ведёт на `settings/queue-00K/index.html`, остальные параметры
  ссылки сохраняются.
- **История** — строки всех страниц консоли сливаются в один документ
  (`history/index.html`), каждая строка несёт `data-a`/`data-b` (участников);
  листание — клиентское.
- **Клиентский слой `tools/static/js/mirror.js`** (подключается только в
  read-only): фильтры, чипы, подсветка, счётчики и листание истории (20 записей);
  распределение Elo на аналитике; состояние читается из адреса и синхронизируется
  `replaceState`. Данные слоя — JSON-острова (`#mirror-models`,
  `#mirror-stats-data`) и `<template>`-строки архива, которые кладёт экспортёр;
  навигационные `onchange="this.form.submit()"` в слепке снимаются.
- **Пороги** — предупреждения при истории больше 2000 записей, очереди больше
  500 страниц и объёме слепка больше 200 МБ; сводка в конце сборки; код
  возврата 0 — успех.
- **Обязанность** — при правках серверных фильтров, счётчиков или разметки
  страниц консоли обновлять `mirror.js`; `tools/test_export.py` сверяет состав
  слепка с реестром и падает при смене разметки.

## Архивация моделей

- `status: archived` в data/models.yaml
- История сохраняется, старые вердикты участвуют в пересчёте
- Серверная таблица поддерживает фильтр active/all/archived
- Архивные модели исключаются из рекомендаций
- `python tools/archive_model.py <id>` / `--restore <id>`

## Масштаб

- 1–10 задач (создаются редко, 1 на 2–3 недели)
- ~33 активных сейчас; целевой запас — до 1000 активных (архивные хранятся)
- 10 000–50 000 вердиктов
- data/matchups/journal.jsonl — ~0.5 КБ на событие (~5 МБ при 10 000)
- data/index.json — ~0.31 КБ на вердикт (~3.5 МБ при 10 000)

## Известные дефекты MVP (зафиксированы в спеках, исправляются отдельно)

- Сервер не проверяет наличие ответов при записи вердикта
