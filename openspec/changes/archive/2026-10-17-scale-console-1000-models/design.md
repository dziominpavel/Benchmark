# Design

## Context

См. `proposal.md` — Why. Состояние на момент планирования:

- Журнал вердиктов — 535 отдельных JSON-файлов `data/matchups/T-001/NNN.json`;
  `data/matchups/state.json` хранит только `next_seq`. `load_matchups()` перечитывает
  и парсит все файлы на каждый вызов; `matchups_digest()` хэширует путь и байты
  каждого файла; порядок реплея — `matchup_sort_key` (seq, legacy-фолбэк
  `(date, _matchup_id)`).
- Запись — единственная точка `record_verdict()` (`tools/elo.py`), вызывается CLI
  `tools/record_verdict.py` и веб-UI: JSON-файл → `state.json` → полный реген
  `data/index.json`.
- Сервер (`tools/server.py`, Flask dev server, `threaded=True`): `ensure_index()`
  парсит `index.json` дважды за запрос; `get_pair_stats()` /
  `get_pair_task_verdicts()` — полный проход по файлам на каждый запрос; рематч-режим
  рекомендаций строит записи для всех `C(M,2)` пар; `render_template_string`
  компилирует шаблон на каждый рендер (~21 мс).
- Замеры проб сессии (temp-скрипты, `bench_probe7_worstcase.py` и др.): сейчас клик
  ~0.4 с @535 вердиктов; без изменений на 1000 моделей / 10k вердиктов — клик ~13.7 с,
  запись ~9–10 с; эмуляция целевой архитектуры — клик ~0.2 с, запись ~0.2–0.4 с,
  худшие ветки (все флаги; рематч 500k пар) — 0.13–0.32 с каждая; sha256 JSONL 3.4 МБ
  ≈ 12 мс.
- Ограничения: только stdlib + Flask; файлы данных — источник правды и живут в git;
  контракт `data/index.json`, формула ELO и семантика pairing/coverage не меняются;
  хост — Windows (файловые локи); тесты — скрипты `tools/test_elo.py`,
  `tools/test_pairing.py`.

Попутно замечено (вне scope этого change): в `openspec/specs/elo-engine/spec.md`
(«История изменений ELO») осталось упоминание `after_matchup`, запрещённого
`data-storage`; сценарий с `general/001` — исторический. Purpose
`matchup-management` («пишет `matchups/<task-id>/NNN.json`») обновляется вручную при
реализации — Purpose не выражается дельтой спеки.

## Goals / Non-Goals

**Goals:**

- Хранение: единый append-only `data/matchups/journal.jsonl`; детерминированный реген
  индекса; полная идентичность реплея до/после миграции.
- Чтение: стоимость повторного запроса не зависит от объёма накопленных вердиктов —
  memo производных структур в процессе сервера.
- Бюджеты спек (leaderboard-ui «Отзывчивость консоли на целевом масштабе»,
  data-storage «Масштаб хранилища»): типичный клик ≤0.5 с, предельный ≤1 с, запись ≤1 с
  при 1000 моделях и 10 000 событиях.

**Non-Goals:**

- БД/внешние брокеры; инкрементальный реген `index.json` как обязательство (полный
  реген сохранён).
- Изменение формата `index.json`, формулы ELO, UI-поведения.
- Витрина `web/` и её подрезка (см. Open Questions).
- Legacy-чтение старого формата в продукт-коде: миграция выполняется до запуска нового
  кода; чтение файлов живёт только внутри скрипта миграции (см. Migration Plan).

## Decisions

### D1. Формат и схема журнала

`data/matchups/journal.jsonl` — UTF-8, одна JSON-строка на событие, append-only,
коммитится в git. Событие вердикта = текущая схема вердикта + поле `matchup`
(`T-NNN/NNN`). Событие аннулирования = `matchup`, `seq`, `task`, `void_of`, `reason`,
`date`, `recorded_at`. `seq` — глобальный (`max+1`); `NNN` — внутри задачи
(`max+1`); `data/matchups/state.json` удаляется, `next_seq` больше не хранится.
Загрузчик возвращает события в порядке `seq` и заполняет `_matchup_id` из `matchup`
(контракт `load_matchups()` не меняется); `_file` = `data/matchups/journal.jsonl`
(диагностическое поле, нигде не читается).

Отклонено: шардинг по таскам (дайджест и парс снова зависят от числа файлов);
SQLite (бинарь вне git, конфликты мержа, новая зависимость); один JSON-массив
(перезапись всего файла на каждую запись, шумные diff).

### D2. Append-протокол и целостность

Запись: эксклюзивный межпроцессный lock на файл журнала (`msvcrt.locking` на Windows /
`fcntl.flock` на POSIX, helper с ретраями и таймаутом); открыть `a`; сериализовать
строку (`json.dumps(..., ensure_ascii=False)`); одним `write` записать строку + `\n`;
`flush` + `os.fsync`; снять lock. Читатели lock не берут: append-only и цельные строки
достаточны. Оборванная последняя строка (краш между write и fsync) игнорируется при
чтении с предупреждением; невалидная строка не последней, дубликаты `seq`, висячие
`void_of` — проблемы `--check`.

Отклонено: tmp-файл + `os.replace` на весь журнал (O(N) на запись); запись без lock
(потеря конкурирующего события); блокировка на чтение (не нужна, стоимость).

### D3. Memo-слой и инвалидация

Минимальный модуль `tools/data_cache.py`: `DataKey` = (дайджест журнала, sha256
содержимого управляющих файлов: `models.yaml`, `answer_flags.yaml`, `settings.yaml`,
`lookups.yaml`) и фабрика мемо `cached(key, name, builder)`. Дайджест журнала
считается через sha256 и кэшируется по `(mtime_ns, size)` самого файла, поэтому на
неизменных данных запрос не хэширует мегабайты; управляющие файлы малы, их хэш честно
пересчитывается (точностей ради — не полагаемся на mtime). Все производные memo
(разобранные события, `pair_stats`, `pair_task_verdicts`, покрытие, рекомендации,
тренды, объект `index.json`, карты имён, флаги) живут под одним ключом в процессе
сервера; сборка — под `threading.Lock` (Flask `threaded=True`), наружу отдаются
неизменяемые построенные значения.

Отклонено: файловый кэш на диске (новый формат, git-шум); `functools.lru_cache`
(ключуется аргументами, не данными); пересчёт на каждый запрос (бюджеты не держатся в
предельных ветках).

### D4. Алгоритмы чтения под 1000 активных

- Рекомендации: обычный режим — перебор только моделей с флагами ответов на активные
  таски; рематч-режим — streaming top-K (`heapq.nsmallest` с ключом сортировки) без
  построения словарей `_build_rec` для всех `C(M,2)` пар; `pair_games` берётся из
  memo `pair_stats`.
- Покрытие: один проход по событиям, знаменатель — пары размеченных моделей;
  `pair_task_verdicts` мемоизируются.
- Тренды: `compute_rank_trends` — один проход по `elo_history` с накоплением ранга
  (было — перескан на каждую модель).
- `ensure_index()` читает `index.json` один раз за запрос, `is_index_stale(idx)` 
  работает с уже прочитанным объектом (устранение двойного парса).

### D5. Запись и аннулирование

`record_verdict()`: под lock — парс журнала (≈30–50 мс на 10k), `seq = max+1`,
`matchup = task/max+1`, снэпшот ELO полным реплеем (как сейчас), append + fsync,
`generate_index()` + `save_index()`, сброс memo-ключа. Скорость записи не зависит от
числа файлов — O(N) по событиям один раз. `void_matchup()`: проверка цели по событиям
журнала, tombstone-строка, реген индекса. `load_state`/`save_state` и
`next_matchup_path` удаляются; появляется `next_matchup_id(task)`.

### D6. Скрипт миграции `tools/migrate_journal.py`

По образцу `migrate_recorded_at.py` (stdlib, `--dry-run`):

1. Abort, если `journal.jsonl` уже существует (идемпотентность).
2. Собрать события из `data/matchups/T-NNN/*.json` (собственный reader — продукт-код
   старый формат не читает), `matchup` восстанавливается из пути; файлы без `seq` —
   abort с перечнем.
3. Отсортировать по `matchup_sort_key`; дубликаты `seq` — abort.
4. `expected` = полный реплей из файлов (модели ELO/games/wins/losses/draws,
   `elo_history` целиком, счётчики summary).
5. Записать журнал во временный файл + `os.replace`.
6. `actual` = реплей из журнала; полное сравнение с `expected`; при расхождении —
   удалить журнал, exit 1 (старые файлы не тронуты).
7. `generate_index()` + `save_index()`; `--check` должен пройти.
8. Удалить старые файлы и `state.json`; напечатать сводку (535 → 535 строк).

Отклонено: миграция «на лету» при первом старте (скрытая запись из читателя);
хранение обратной совместимости в продукт-коде (мёртвая ветка, усложняет `--check`).

### D7. Шаблоны

`render_template_string` заменяется на предкомпилированные `Template`-объекты (один
`Environment`, компиляция на импорте/первом обращении и переиспользование) — минус
~21 мс на рендер; содержимое шаблонов не меняется.

### D8. Постраничная очередь на `/settings`

Полный список открытых ячеек остаётся доступным, но страница рендерит только
текущую сотню строк (`queue_page`, 100 строк на страницу; выход за диапазон —
граничная страница). Материализуется только нужный префикс: top-(offset+100)
рекомендаций берётся потоковым `heapq.nsmallest` (memo по числу строк) и режется
срезом; разбивка остатка по таскам считается по `pair_task_verdicts` (C(k,2) минус
закрытые ячейки) без материализации очереди. При 1000 моделях очередь достигает
~500k ячеек — полный рендер занимал 6–9 с; первая страница укладывается в бюджет
`/settings` ≤1 с (замер 0.84 с), тёплые и соседние страницы — 0.05–0.3 с.
Крайний случай — последняя страница предельного списка: top-N близится к полному
(`~2 с` на синтетике 1000/10k), в бюджет не нормируется.

## Risks / Trade-offs

- [Оборванная строка при краше] → предупреждение при чтении + fsync при записи +
  `--check`; теряется только последнее событие, координатор перезапишет вердикт.
- [Гонка записи сервер + CLI] → межпроцессный lock на журнале; тест с двумя
  процессами.
- [Устаревшее memo] → ключ включает sha256 управляющих файлов и дайджест журнала;
  правки через скрипты всегда меняют содержимое; рестарт сервера — страховка.
- [Windows-локи: `msvcrt.locking` блокирует байтовый диапазон] → helper с ретраями и
  минимальным временем удержания (только append).
- [Холодная сборка memo в предельной ветке ~0.6 с] → бюджет предельного клика 1 с;
  повторные запросы — мемо.
- [Рост данных: 50k событий ≈ 15–20 МБ журнала, ~17 МБ index.json] → приемлемо для
  git; витрина `web/` — отдельный порог (Open Questions).
- [Ошибка миграции] → верификация полным сравнением до удаления файлов; файлы
  остаются в git-истории.

## Migration Plan

1. Реализация в репозитории: `elo.py` (journal I/O), `data_cache.py`, `server.py`
   (memo, алгоритмы, шаблоны), `render_helpers.py`, `migrate_journal.py`, тесты,
   доки, скиллы.
2. Валидация в изолированной копии: миграция на реальных 535 файлах, `--check`,
   смоук UI, перф-guard на синтетике 1000/10k.
3. Выкат в рабочем репозитории: остановить сервер → `tools/migrate_journal.py` →
   `python tools/elo.py --check` → старт сервера → смоук; коммит — по команде
   пользователя.
4. Откат: до шага удаления старых файлов скрипт сам не трогает данные; после —
   `git checkout -- data/` возвращает файлы, журнал удаляется, повторная миграция
   воспроизводима.

## Open Questions

- Витрина `web/`: при 10 000 вердиктов `index.json` ≈ 4+ МБ. Решение о подрезке
  (частичный `elo_history`, пагинация по файлам) откладывается до достижения порога —
  10 000 вердиктов или размер `index.json` >4 МБ. На текущий change не влияет.
