## Context

См. `proposal.md` — мотивация. Текущее состояние: `pairing-algorithm` ранжирует пары моделей глобально (`tools/server.py::get_recommendations`), не разбираясь по таскам. UI (`tools/server.py::INDEX_TEMPLATE`) показывает имя, ELO, `h2h_label` и обоснование. Форма «Записать результат» требует выбрать модель A, модель B и таск; таск по умолчанию — `current_task` из `data/settings.yaml`. `data/index.json` (генерируется `tools/elo.py::generate_index`) уже содержит `tasks.<id>.answers` и `matchups_count` по таскам.

## Goals / Non-Goals

**Goals:**
- `get_recommendations` вычисляет `recommended_task` для каждой пары.
- Блок рекомендаций показывает `recommended_task` и пометку об отсутствии ответов.
- Кнопка «Прогнать» подставляет `model_a`, `model_b` и `recommended_task` в форму.

**Non-Goals:**
- Изменение ранжирования пар или ELO-логики.
- Изменение формата `data/index.json` или `data/matchups/`.
- Создание отдельных страниц/роутов.
- Автоматическая проверка наличия ответов перед записью вердикта (только визуальная пометка).

## Decisions

1. **Глобальное ранжирование пары сохраняем, `recommended_task` — атрибут отображения.**
   - Рationale: меньше изменений, не ломает текущий `pairing-algorithm` и `run-progress`. Ранжирование по глобальным `pair_games` всё ещё корректно направляет на новые модели.
   - Alternatives: ранжировать ячейки `(таск, пара)` — более радикально, требует пересмотра спеки `pairing-algorithm` и влияет на порядок рекомендаций.

2. **`recommended_task` = первый активный таск по лексикографическому порядку `T-NNN`, в котором у пары нет неаннулированного вердикта.**
   - Rationale: соответствует сценарию пользователя — сначала закрыть `T-001` для новой модели, затем `T-002`.
   - Alternatives: текущий таск, случайный пустой таск, таск с наименьшим покрытием — отклонены, потому что ломают предсказуемый порядок догона.

3. **Проверка наличия ответов через `data/index.json["tasks"][<task>]["answers"]` (или прямой glob `data/answers/<task>/*.md`).**
   - Rationale: `index.json` уже содержит этот список, пересчитывается при изменении ответов.
   - Alternatives: отдельный индекс ответов — избыточно.

4. **JS `usePair(a, b, task)` принимает три аргумента и выставляет `taskField`.**
   - Rationale: минимальное изменение клиентского кода.
   - Alternatives: серверная подстановка в отдельной сессии — усложняет без причины.

5. **Рекомендация показывается даже при отсутствии ответов, с пометкой «нужны ответы».**
   - Rationale: пользователь хочет видеть, что пару надо прогнать; подготовка ответов — отдельный шаг воркфлоу (`@benchmark-run-a` / `@benchmark-run-b` или ручной).

## Risks / Trade-offs

- **Risk**: `recommended_task` может указывать на таск, где у одной или обеих моделей нет ответа, и форма вердикта при этом будет валидна (модели разные, таск активен). Пользователь может попытаться записать вердикт без ответов.
  - **Mitigation**: визуальная пометка «нужны ответы»; воркфлоу подразумевает, что перед судейством ответы готовятся отдельно.

- **Risk**: при большом числе активных тасок и моделей вычисление `recommended_task` для каждой пары может стать дорогим.
  - **Mitigation**: количество активных тасок на практике невелико; алгоритм остаётся `O(C(n,2) × |tasks|)` и выполняется только при рендеринге страницы.

- **Trade-off**: использование глобальных `pair_games` вместо `pair_games` по конкретному таску. Это значит, что после частичного заполнения `T-002` рекомендации могут предлагать пары с большим глобальным `pair_games` раньше, чем пары с `pair_games=0` на `T-002`. Однако тир калибровки и близость ELO по-прежнему отдают приоритет новым/малоигравшим моделям.
