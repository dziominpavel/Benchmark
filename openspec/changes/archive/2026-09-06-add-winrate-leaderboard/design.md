## Context

Текущий leaderboard хранит в `index.json` для каждой модели: `elo`, `games`, `wins`, `losses`, `draws`. Серверная таблица (`tools/server.py`) и статический экспорт (`tools/generate_html.py`) рендерят одни и те же счётчики, но не выводят производный `winrate`. Для реализации новой колонки достаточно существующих данных, пересчёт `index.json` и `elo.py` не требуются. Подробнее о мотивации — в `proposal.md`.

## Goals / Non-Goals

**Goals:**
- Добавить колонку `Винрейт, %` в серверную и статическую таблицы leaderboard.
- Вычислять значение из `wins` и `games` единообразно в обоих рендерах.
- Сохранить ELO как единственный критерий сортировки.
- Обработать `games == 0` без `ZeroDivisionError`.

**Non-Goals:**
- Изменение схемы `index.json` или полей модели.
- Изменение ELO-движка, pairing-алгоритма, модельного реестра.
- Добавление сортировки по winrate.
- Показ winrate в CLI, `index.json` или API вне HTML.

## Decisions

### 1. Вычислять winrate при рендеринге, а не хранить в `index.json`

**Выбрано:** значение `wins / games * 100` вычисляется непосредственно в `tools/server.py` и `tools/generate_html.py`.

**Рationale:** `wins` и `games` уже есть в `index.json`; winrate — чистая производная. Хранение дополнительного поля в `index.json` дублировало бы данные, усложнило `elo.py` и потребовало изменения `data-storage` спеки. Рендеринговое вычисление сохраняет единый источник истины.

**Alternative considered:** добавить `winrate` в `generate_index()` / `recalculate()`. Отклонено: избыточно для UI-метрики, требует спек и тестов ELO-движка.

### 2. Общий helper `format_winrate(wins, games)` в `tools/render_helpers.py`

**Выбрано:** вынести форматирование в `render_helpers.py`, который уже используется `server.py` и `generate_html.py`.

**Рationale:** избегает дублирования логики и форматирования между двумя рендерами; легко покрыть юнит-тестом при необходимости.

**Alternative considered:** копировать inline-вычисление в `server.py` и `generate_html.py`. Отклонено: при изменении формата пришлось бы править два места.

### 3. Формула: `wins / games * 100`, формат `X.Y%`, `games == 0` → `—`

**Выбрано:** `f"{(wins / games) * 100:.1f}%"` при `games > 0`, иначе строка `—`.

**Rationale:** один знак после запятой даёт достаточную детализацию для малых выборок (`1/3` → `33.3%`) и при этом компактен. Процент с `%` в заголовке делает единицу измерения очевидной. `—` при нуле игр корректнее, чем `0.0%`, так как метрика не определена.

**Alternative considered:** `wins / (wins + losses)`, то есть без ничьих. Отклонено: пользователь запросил отношение побед к общему количеству игр; ничьи — это тоже игры, их исключать некорректно.

### 4. Колонка после `games` / `Всего`, заголовок `Винрейт, %`

**Выбрано:** размещать новую колонку последней, сразу после общего числа игр.

**Rationale:** не ломает привычный порядок существующих колонок (`ELO | Побед | Поражений | Ничьих | Всего | Винрейт, %`). Расположение рядом с `games` подчёркивает связь метрик.

**Alternative considered:** разместить сразу после `ELO`. Отклонено: это могло бы натолкнуть на мысль, что winrate участвует в ранжировании, и создало бы визуальный акцент на второстепенной метрике.

### 5. Интеграция с серверным Jinja-шаблоном

**Выбрано:** передать `format_winrate` в контекст `render_template_string` для основного шаблона leaderboard и вызывать его внутри `INDEX_TEMPLATE`.

**Rationale:** `server.py` использует `render_template_string` с inline-шаблонами. Поскольку helper импортирован в модуле, достаточно добавить `format_winrate=format_winrate` в `render_template_string(..., format_winrate=format_winrate)`. Это проще и локальнее, чем регистрация Jinja-global.

**Alternative considered:** добавить `format_winrate` в `app.jinja_env.globals`. Отклонено: требует понимания, как Flask-Environment инициализируется в `server.py`, и даёт глобальный сайд-эффект ради одного шаблона.

### 6. Интеграция со статическим `generate_html.py`

**Выбрано:** при формировании `ROW_TEMPLATE` заменить плейсхолдер `{winrate}` на результат `format_winrate(m.get("wins", 0), m.get("games", 0))`.

**Rationale:** `generate_html.py` не использует Jinja, а собирает HTML через `str.replace`. Вычисление в том же цикле, где заполняются `wins`/`losses`/`draws`/`games`, — минимальная и понятная вставка.

## Risks / Trade-offs

- **[Risk]** Таблица станет шире на узких экранах.
  - **Mitigation:** CSS уже требует `overflow-x: auto` в `.table-wrap`; новая колонка уложится в существующую прокрутку. Контент `th`/`td` имеет `white-space: nowrap`.

- **[Risk]** Пользователи могут интерпретировать winrate как основной рейтинг.
  - **Mitigation:** сортировка остаётся по ELO; колонка расположена в конце; заголовок содержит `%`, что указывает на производную метрику, а не на рейтинг.

- **[Risk]** При `games == 0` неверная обработка приведёт к `ZeroDivisionError`.
  - **Mitigation:** helper `format_winrate` явно проверяет `games > 0` и возвращает `—`.

- **[Risk]** Дублирование форматирования при неявном округлении.
  - **Mitigation:** единый helper с `:.1f` в обоих рендерах.

## Migration Plan

Миграция не требуется. Изменение чисто UI-уровня, `index.json` и `matchups/` не затрагиваются. После деплоя достаточно перегенерировать `leaderboard.html` (`python tools/generate_html.py`) или перезапустить `tools/server.py`.
