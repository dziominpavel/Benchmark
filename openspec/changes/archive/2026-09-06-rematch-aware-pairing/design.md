## Context

Текущее состояние: `get_all_matchup_pairs()` в `tools/server.py`
собирает `set` из `frozenset({a, b})` по всем вердиктам журнала, а
`get_recommendations()` отбрасывает любую пару из этого множества.
Журнал `matchups/` append-only и уже содержит всю историю встреч —
данные для счётчика есть, схема вердиктов не меняется.
Мотивация — см. proposal.md (Why).

## Goals / Non-Goals

**Goals:**

- Пары перестают быть одноразовыми: после завершения круга
  рекомендации продолжают предлагать осмысленные бои (рематчи).
- Приоритет — парам с меньшим числом встреч: самобалансировка
  без ручного управления.
- Нулевое изменение поведения, пока есть несыгранные пары.

**Non-Goals:**

- Разрез рекомендаций по задачам (решено: не нужен, журнал
  глобален — счётчик тоже глобален).
- Лимит разницы ELO (решено: не вводим — мисматчи это канал
  коррекции рейтинга, см. обсуждение).
- Потолок на число рематчей одной пары.
- Изменения в ELO-движке, журнале вердиктов, форме вердикта
  (ручные рематчи она и так допускает).

## Decisions

**D1: `Counter` вместо `set` для истории пар.**
`get_all_matchup_pairs()` заменяется на функцию, возвращающую
`dict[frozenset, int]` — число применённых вердиктов пары.
Логика пропуска tombstone-/аннулированных вердиктов сохраняется
как есть: аннулированная игра не считается. Альтернатива —
оставить `set` и отдельно считать счётчик — отвергнута: двойной
обход журнала без выигрыша.

**D2: `pair_games` — первичный ключ сортировки, до тира.**
Порядок: `(pair_games ↑, tier ↑, -score ↓)`. Рассматривался
вариант `(tier, pair_games, -score)` — тогда рематч с участием
некалиброванной модели (тир 1) обгонял бы никогда не игравшую
пару двух опытных (тир 2). Это нарушает принцип «сначала
закончить круг», поэтому выбран счётчик первым. Внутри одного
числа встреч порядок прежний: тир → близость ELO, т.е. рематчи
всплывают в порядке «наименее игравшие и наиболее равные».

**D3: Без потолка рематчей.**
Пара с 5 встречами проигрывает паре с 2 — механизм сам
балансирует, искусственный cap ничего не добавляет, кроме
нового параметра для тюнинга. Альтернатива (cap, скажем, на
3–5 встреч) отложена: если появится, это одна строка в фильтре
кандидатов, спека это допускает.

**D4: Причина рематча — отдельная ветка.**
`pair_games > 0` → «рематч (встречались N раз)», без разбора
`min_games`/`elo_diff`: у сыгранной пары обе модели уже играли,
«новая модель» невозможна, а Δ-формулировки малоинформативны
для рематча — важен сам факт повторной встречи и её номер.

**D5: Пустое состояние блока рекомендаций упрощается.**
Ветка «Все пары уже прогнаны…» в `INDEX_TEMPLATE` становится
недостижимой при ≥2 моделях (пустой `recommendations` теперь
означает только <2 активных). Текст заменяется на нейтральный
или удаляется — зафиксировано в дельта-спеке leaderboard-ui.

## Risks / Trade-offs

- Блок рекомендаций никогда не «заканчивается» → причина
  «рематч (N раз)» делает состояние прозрачным; пользователь
  всегда видит, что круг пройден.
- Счётчик глобален по задачам → рематч, сыгранный на другой
  задаче, тоже инкрементирует пару. Осознанно: разрез по
  задачам исключён из скоупа, ELO и так считает всё в кучу.
- `pair_games` считается обходом журнала при каждой отрисовке
  страницы → журнал мал (десятки файлов), стоимость
  пренебрежима; при росте можно кэшировать в `index.json`.

## Migration Plan

Миграции нет: формат вердиктов и `index.json` не меняются,
счётчик вычисляется из существующего журнала. Откат — возврат
`get_all_matchup_pairs`/`get_recommendations` к прежней логике;
журнал затронуть не может.
