# Design

## Context

Сейчас `build_elo_series()` (`tools/render_helpers.py`) строит общую
порядковую шкалу: каждый матч с участием выбранных моделей получает следующий
индекс, а точка модели появляется только в её матчах. `build_elo_multiline_svg()`
раскладывает эти индексы равномерно по ширине и подписывает только края датами
первого и последнего матча выборки. Поэтому 37 матчей одного вечера могут
занимать около 22% ширины, а концы линий выглядят как разные даты, хотя все они
приходятся на 20.10.2026.

`tools/server.py` передаёт в построитель `series_data["x_count"]` и
`series_data["dates"]`, а легенда берёт текущий ELO из реестра. Статический
слепок использует тот же серверный SVG; отдельного JS-рендера «Динамики ELO»
в `tools/static/js/mirror.js` нет — клиентский порт перерисовывает только
карточку «Рейтинг».

См. `proposal.md` — Why; требования — в
`specs/leaderboard-ui/spec.md` (delta).

## Goals / Non-Goals

**Goals:**

- Сделать ось X календарной: расстояние между точками пропорционально дням.
- Оставить одну точку на модель в день — ELO после последнего матча дня.
- Сделать окно оси стабильным: оно зависит от периода и истории, но не от
  набора выбранных моделей.
- Показать дату последнего матча в подсказке конца линии и промежуточные даты
  на оси.
- Сохранить выбор моделей, легенду с текущим ELO, ссылки в профиль, пустые
  состояния и фильтр 30/90/всё.

**Non-Goals:**

- Не менять расчёт ELO и формат журнала/реестра.
- Не добавлять внутридневную детализацию на «Аналитику»: профиль модели
  по-прежнему показывает каждый матч.
- Не менять клиентский порт слепка: карточка «Динамика ELO» остаётся
  серверным SVG, перерисовка фильтров её не затрагивает.
- Не добавлять новые зависимости и не менять API страницы, кроме формы SVG.

## Decisions

### 1. Календарная ось с дневной агрегацией

По X откладывается номер календарного дня в окне периода. Для каждой модели и
каждого дня с матчами строится одна точка: ELO `after` последнего матча этого
дня в порядке `seq`. Если в дне несколько матчей, побеждает последний по `seq`;
если у последнего матча нет `after`, берётся последний матч дня с непустым
`after`. Дни без матчей точки не получают, линия заканчивается в день
последнего матча модели.

Почему так: это ровно вариант «одна точка в день», который выбрал пользователь.
Он убирает внутридневные вертикальные всплески и делает конец линии датой, а не
позицией в очереди матчей.

Альтернативы:

- **Ось по `recorded_at` (timestamp).** Сохраняет порядок матчей и внутридневную
  деталь, но матчи одного прогона часто имеют одинаковый timestamp; линия
  превращается в вертикальную стену, а «календарность» остаётся условной.
- **Оставить порядковую ось и только подписать концы.** Дешевле, но не решает
  исходную проблему: расстояние по X всё равно не время.

### 2. Окно периода не зависит от выбора линий

`end` — максимальная валидная дата истории. `start`:

- `period=30`: `max(min_date, end - 29 дней)`;
- `period=90`: `max(min_date, end - 89 дней)`;
- `period=all`: `min_date`.

`day_count = (end - start).days + 1`. Если валидных дат нет, окно пустое и
карточка показывает пустое состояние.

Почему так: при смене набора моделей даты по X не должны переезжать; иначе
сравнивать графики между собой нельзя. Обрезка по `min_date` не оставляет
пустого поля до начала истории. Для одной новой модели в режиме «всё» линия
будет короткой в правой части — это честно показывает, что модель новая; для
зума есть период 30 дней.

Альтернативы:

- **Окно по выбранным матчам.** При выборе одной новой модели окно сжимается до
  одного дня и график вырождается; при смене линий ось прыгает. Отклонено.
- **Фиксированное окно 30/90 дней без обрезки.** Появляется пустое поле до
  первой даты истории; для `all` всё равно нужна обрезка. Отклонено.

### 3. Контракт `build_elo_series()`

Функция возвращает:

```python
{
    "window": ("YYYY-MM-DD", "YYYY-MM-DD") | (),
    "day_count": int,
    "series": {mid: [(day_index, elo), ...]},
    "match_counts": {mid: int},
    "match_count": int,
}
```

- `day_index` — `(day - start).days`, от 0 до `day_count - 1`; точки отсортированы
  по возрастанию.
- `series` содержит ключ для каждой выбранной модели, даже если список точек
  пуст.
- `match_counts[mid]` — число матчей модели в окне; `match_count` — общее число
  матчей окна (каждый матч считается один раз, даже если обе стороны выбраны).
- Матчи без валидной даты не попадают в серию и счётчики: их некуда поставить на
  календарной оси.

Такое представление оставляет построителю SVG простую линейную раскладку:
`day_index` уже нормализован, а `window` даёт даты для подписей и подсказок.

Альтернатива: хранить в точках `(date_string, elo)` и парсить даты в SVG.
Гибче, но дублирует разбор и усложняет тесты; отклонено.

### 4. SVG: подписи, тики и подсказки

`build_elo_multiline_svg(series, window, match_count=0, ...)`:

- `x(i)` — та же линейная раскладка, но `i` — `day_index`, а число позиций —
  `day_count`. При `day_count == 1` точка центрируется.
- На оси до пяти равномерных тиков: начало, четверть, середина, три четверти,
  конец. Для короткого окна лишние тики отбрасываются, дубликаты не рисуются.
  Подписи — `DD.MM.YYYY`; крайние прижаты к краям (`start`/`end`), средние
  центрированы. Это даёт календарную привязку, не вводя «красивых» интервалов.
- `aria-label`: `Динамика ELO: линий N, матчей M, дней D`.
- Подсказка линии: `name: N матчей, M дней, последний матч DD.MM.YYYY, Elo X`.
  Числа согласуются через `plural_ru()`.
- Подсказка точки конца: то же, но с акцентом на дату последнего матча.
- Цвета, опорная линия 1200, кликабельная ссылка `/model/<id>`, прозрачный
  хит-слой и точка конца сохраняются.

Сервер добавляет в элемент серии `matches` из `match_counts[mid]`, чтобы
подсказка показывала число матчей, а не число дневных точек.

### 5. Краевые случаи

- Нет истории или нет валидных дат → пустое окно, SVG не строится, карточка
  показывает пустое состояние.
- У выбранной модели нет матчей в окне → её линия пустая, легенда показывает
  «нет матчей в периоде»; ось при этом остаётся общей.
- История короче 30/90 дней → окно начинается с первой даты истории.
- Матч с датой вне окна → не участвует.
- Матч без даты/с невалидной датой → пропускается.
- Несколько матчей в один день → одна точка, последний `after` по `seq`.
- Обратная дата (запись сделана позже, дата вердикта раньше) → точка ставится на
  дату вердикта; это известное ограничение календарной агрегации, отдельной
  миграции данных нет.

## Risks / Trade-offs

- **Теряется внутридневная деталь.** 37 матчей за 33 минуты превращаются в одну
  точку. Смягчение: профиль модели сохраняет график по каждому матчу; в
  подсказке видно число матчей дня.
- **Легенда показывает текущий ELO, а конец линии — ELO на последнем матче
  периода.** При `period=30/90` это может быть одно и то же не всегда. Смягчение:
  подсказка конца явно называет дату последнего матча; поведение легенды не
  меняется.
- **Обратные даты могут дать немонотонную линию.** Смягчение: дата вердикта —
  источник истины; при необходимости позже можно перейти на `recorded_at`.
- **Новые модели в режиме «всё» выглядят коротким отрезком справа.** Это честная
  картина; для детального просмотра есть 30 дней и профиль.
- **Пять подписей на узком SVG могут пересечься.** Смягчение: крайние подписи
  прижаты к краям, средние центрированы; при коротком окне число тиков
  уменьшается.
- **В рабочей копии уже есть незакоммиченные правки соседнего change
  `fix-rating-group-legend` в тех же файлах.** Смягчение: перед началом
  зафиксировать `git diff`, не перезаписывать чужие ханки и согласовать
  конфликт с владельцем, если он возникнет.

## Migration Plan

Миграции данных нет. Порядок выката: обновить построение серий и SVG, обновить
вызов в `server.py` и подпись карточки, обновить тесты и документацию, пересобрать
статический слепок. Откат — возврат кода и повторная сборка слепка; данные
бенчмарка не затрагиваются.
