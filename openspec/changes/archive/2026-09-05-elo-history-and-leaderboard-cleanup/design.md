## Context

См. `proposal.md` — мотивация и scope. Здесь описывается, как технически перевести историю ELO с модель-центричного формата на матч-центричный, починить `recorded_at`, и закрыть сопутствующие дефекты.

## Goals / Non-Goals

**Goals:**
- Сделать `elo_history` в `index.json` одной записью на матч.
- Обеспечить `recorded_at` во всех `matchups/*.json` (реальных для новых, синтетических для legacy).
- Синхронизировать `openspec/specs/` с реальным форматом `index.json` и журнала.
- Починить извлечение `task_id` из имени директории.
- Исключить архивные модели из рекомендаций и добавить их визуальную пометку.
- Исправить нумерацию файлов в `server.py`.

**Non-Goals:**
- Перевод хранилища с файлов на БД.
- Удаление дублирования skills в `.devin/`, `.cursor/`, `.opencode/`.
- Полная визуальная редизайн-морды leaderboard.
- Конкурентная запись вердиктов (остаётся single-user Flask).

## Decisions

### 1. Формат `elo_history` — одна запись на матч

**Решение:** `elo_history` содержит одну запись на вердикт.

```json
{
  "matchup": "general/006",
  "after_matchup": "general/006",
  "seq": 7,
  "date": "2026-09-05",
  "recorded_at": "2026-09-05T19:32:13+03:00",
  "model_a_id": "devin-swe-1-7-max",
  "model_b_id": "devin-glm-5-2-high",
  "winner": "b",
  "elo_a": {"before": 1200, "after": 1219, "delta": 19},
  "elo_b": {"before": 1180, "after": 1161, "delta": -19}
}
```

**Почему:**
- Соответствует ментальной модели пользователя: один матч — одна строка.
- Исключает дублирование общих полей (`date`, `recorded_at`, `seq`, `matchup`).
- Упрощает UI-рендеринг: `server.py` и `generate_html.py` читают одну и ту же структуру.

**Альтернатива:** оставить две записи и склеивать их при рендере. Отклонена, потому что лог остаётся неестественным, а спеки/код всё равно придётся менять.

### 2. Сохранить `elo_history` в `index.json`

**Решение:** оставить `elo_history` в `index.json` как производную проекцию.

**Почему:**
- `index.json` и так считается кэшем; он перегенерируется из `matchups/`.
- UI получает всё одним чтением файла.
- Масштаб заявлен как <500 вердиктов — размер `elo_history` останется <30 KB.

**Альтернатива:** вынести историю в отдельный `history.json`. Отклонена — лишняя сущность без ощутимой выгоды на текущем масштабе.

### 3. Бэкфилл `recorded_at` по `seq`

**Решение:** для существующих `matchups/general/*.json`, в которых `recorded_at` отсутствует, проставить синтетическое время на основе `seq`:

```
recorded_at = "{date}T00:00:{02+seq:02d}+00:00"
```

для `general/001` (seq=2) → `2026-09-05T00:00:04+00:00`.

**Почему:**
- Сохраняет монотонность `recorded_at` относительно `seq`.
- Даёт UI точное поле `recorded_at` без догадок.
- Git не гарантирует `mtime`, файл `state.json` не хранит историю записи, поэтому `seq` — единственный объективный источник порядка.

**Риск:** синтетическое время не совпадает с реальным моментом записи. **Митигация:** задокументировать в `design.md` и `tasks.md`, что для новых вердиктов `recorded_at` всё равно будет реальным `now_iso()`.

**Альтернатива:** оставить `recorded_at` пустым. Отклонена — `verify_snapshots` игнорирует пустоту, и `--check` не выполняет свою функцию.

### 4. `recorded_at` становится required

**Решение:** `recorded_at` должен присутствовать во всех `matchups/*.json`. `record_verdict.py` уже пишет его; `generate_index` не будет пытаться его допускать.

**Почему:**
- `matchup-management` спека уже декларирует его обязательным.
- Целостность журнала зависит от возможности проверить монотонность.

### 5. Извлечение `task_id`

**Решение:** `collect_tasks_info` должен брать `task_id` как часть имени директории до второго дефиса: `T-001-recurrence-bugs` → `T-001`.

**Почему:**
- Сейчас `split("-")[0]` даёт `"T"`, что портит сводку.
- Директории задач строго формата `T-NNN-<slug>`.

**Альтернатива:** вынести `task_id` в front matter `task.md`. Отклонена — можно добавить позже, а сейчас достаточно починить парсинг имени.

### 6. Архивные модели

**Решение:**
- `get_recommendations` (`tools/server.py`) исключает модели со `status: archived`.
- `generate_html.py` и `server.py` добавляют маркер `(archived)` рядом с именем или серый фон.
- `index.json` включает `status` в секцию `models`, чтобы UI не читал `models.yaml` заново.

**Почему:**
- Архивные модели не должны участвовать в новых сравнениях по умолчанию.
- Их история сохраняется для пересчёта ELO.

### 7. Нумерация matchup-файлов

**Решение:** `next_matchup_path` в `server.py` и `elo.py` должен искать `max(existing_numbers) + 1` вместо `len(files) + 1`.

**Почему:**
- Удаление промежуточного файла сейчас приводит к перезаписи.
- Исправление локально, не влияет на архитектуру.

### 8. Унификация рендера истории

**Решение:** создать общую функцию `format_history_item(item, name_map)` в `tools/elo.py` или отдельный модуль `tools/render_helpers.py`, используемый и `server.py`, и `generate_html.py`.

**Почему:**
- Убирает дублирование логики.
- Упрощает будущие правки формата.

**Альтернатива:** оставить две копии кода. Отклонена — именно дублирование привело к рассинхрону.

## Risks / Trade-offs

| Risk | Mitigation |
|---|---|
| BREAKING-изменение `elo_history` ломает сторонние скрипты, читающие `index.json` | Версия `index.json` поднимается до 3; `version` проверяется в `tools/*.py`. Публичных API нет. |
| Синтетическое `recorded_at` вводит в заблуждение | Чётко пометить в комментарии миграции: synthetic backfill. Новые записи — реальные. |
| `--check` может сломаться, если миграция пройдёт не так | После миграции запустить `python tools/elo.py --check`; добавить его в `tasks.md` как acceptance-критерий. |
| `generate_html.py` и `server.py` рендерят по-разному HTML | Вынести рендеринг в общую helper-функцию. |
| Поддержка skills для трёх IDE затруднена | Этот change не трогает skills; их дедупликация — отдельная тема. |

## Migration Plan

1. **Создать/обновить OpenSpec-артефакты** (proposal, design, specs, tasks).
2. **Обновить `tools/elo.py`:**
   - `recalculate` генерирует match-centric `elo_history`.
   - `generate_index` пишет `index.version = 3`.
   - `is_index_stale` и `verify_snapshots` учитывают `recorded_at` обязательным.
3. **Обновить `tools/test_elo.py`:**
   - `test_elo_history` проверяет 1 запись на матч.
   - Добавить тест на `recorded_at`.
4. **Создать/запустить `tools/migrate_recorded_at.py`:**
   - Пройтись по `matchups/**/*.json`.
   - Для файлов без `recorded_at` проставить синтетическое на основе `seq` и `date`.
   - Вывести diff для ручной проверки.
5. **Обновить `tools/server.py` и `tools/generate_html.py`:**
   - Общий helper рендера истории.
   - Одна строка на матч.
   - Фильтр/пометка archived.
   - `next_matchup_path` с `max + 1`.
6. **Обновить `tools/archive_model.py`:**
   - Убедиться, что `index.json` регенерируется после смены статуса.
7. **Запустить `python tools/elo.py --check` и `python tools/test_elo.py`.**
8. **Запустить `openspec validate --all`.**
9. **Закоммитить `matchups/` и `index.json`.**

## Open Questions

- Нужно ли поднимать `index.json` version до 3 или достаточно 2? Сейчас `index.json` уже `version: 2`, а спеки говорят `version: 1`. Предлагаю зафиксировать `version: 2` в `data-storage` спеке, а match-centric `elo_history` считать совместимым обновлением внутри version 2 (если потребители ориентируются на поля, а не на version). Если требуется строгая схема — поднимаем до 3.
