## Context

См. `proposal.md` — мотивация. Текущее состояние: `get_recommendations` в `tools/server.py:338` ранжирует пары моделей глобально (`pair_games` → тир → closeness) и вычисляет `recommended_task` как первый активный таск без вердикта пары (`server.py:419-423`), флаги `data/answer_flags.yaml` не читает. `get_coverage` в `tools/elo.py:890` считает ячейки `(таск, пара)` по вердиктам, флаги не читает; знаменатель статичен (`таски x C(n,2)`). `get_answer_matrix` (`elo.py:939`) уже считает долги по флагам, но используется только в `/settings`. Главная (`leaderboard()` + `INDEX_TEMPLATE`) показывает топ-3 с листанием (`showRec`/`nextRec`, счётчик) и статус-бар на статическом покрытии. Договорённость с пользователем из explore: кандидат = только READY, приоритет тасков строгий, топ-1, динамический знаменатель, рематчи — отдельный необязательный режим без учёта флагов и без напоминаний про долги.

## Goals / Non-Goals

**Goals:**
- Обычный режим рекомендаций работает только на READY-ячейках с приоритетом таска первым ключом; внутри таска сохраняется проверенная сортировка (глобальные игры, тир, closeness).
- Прогресс отражает видимую работу (`READY + DONE`), держит инвариант «есть READY → < 100%» и cap 100%.
- UI упрощается до одной карточки без листания; состояние 100% и пустое состояние определены явно.

**Non-Goals:**
- Автоблокировка записи вердикта при отсутствии ответов (форма остаётся валидной по моделям и таску; визуальных пометок про долги на главной нет по решению пользователя).
- Изменение формата `data/index.json`, `data/matchups/`, `data/answer_flags.yaml` и ELO-математики.
- Отдельные страницы/роуты и перенос матрицы ответов на главную.

## Decisions

1. **Кандидат обычного режима — READY-ячейка `(task, pair)`, а не пара.**
   Rationale: иначе нельзя выразить приоритет таска и невидимость BLOCKED; `recommended_task` перестаёт быть «атрибутом отображения» и становится координатой ячейки. Переиспользуем готовые источники: `active_tasks(load_settings())`, `load_answer_flags()`, `get_pair_task_verdicts()` (невердиктность в таске), `get_pair_stats()` (глобальные игры/счёт для сортировки и `h2h_label`).
   Alternatives: оставить кандидатом пару + искать «первый READY-таск пары» — отклонено: пара с BLOCKED `T-001` и READY `T-002` тогда конкурировала бы с чужими READY `T-001` на равных, что ломает строгий приоритет тасков.

2. **Порядок сортировки: таск → `pair_games` → тир → closeness.**
   Rationale: реализует «сначала полностью закрыть T-001»; внутри таска поведение неотличимо от текущего (у всех READY в этом таске по-тасковых игр 0, поэтому глобальные игры/тир/closeness — осмысленные различители опыта и равенства боя).
   Alternatives: по-тасковые игры первым ключом — бессмысленно (все нули); interleaving тасков по closeness — отклонено пользователем.

3. **Топ-1, карусель удалить.**
   Rationale: пользователь всегда берёт первую; при гарантии «всё в топе физически судимо» перебор теряет смысл; меньше JS (`usePair` остаётся с 3 аргументами, `showRec`/`nextRec` и счётчик удаляются).
   Alternatives: оставить топ-3 READY — отклонено как лишний UI без сценария.

4. **Покрытие: `TOTAL = READY + DONE`, `percent = min(100, DONE/TOTAL*100)`.**
   Rationale: BLOCKED исключены с обеих сторон — добавление «пустой» модели не двигает бар, появление флага честно роняет процент; повторы и рематчи не влияют (ячейка уже DONE). Инвариант `< 100%` при `READY > 0` выполняется конструктивно.
   Alternatives: вычитать BLOCKED только из знаменателя, но держать DONE-вердикты BLOCKED-ячеек в числителе — отклонено: снятие флага тогда давало бы процент > 100% и рвало инвариант.

5. **Рематч — fallback без флагов, простая сортировка, пометка в UI.**
   Rationale: когда READY пуст, судить «нечего», но уточнить ELO полезно; логика принципиально не важна (рейтинги уже +/- актуальны), поэтому берём старую тройку без таск-приоритета (`pair_games` → тир → closeness) и `recommended_task = первый активный таск`; вывод `get_recommendations` дополняется признаком режима для пометки «доп. точность: рематч». Напоминаний про долги нет по решению пользователя.
   Alternatives: пустой блок при 100% — отклонено (пользователь хочет крутить рематчи); учитывать флаги и в рематчах — отклонено (тогда при «всё BLOCKED» блок пустовал бы, а пользователь хочет судить рематчи и в этом случае).

6. **Флаги читаются на лету, индекс не меняется.**
   Rationale: `answer_flags.yaml` мал; `get_recommendations` и `get_coverage` вызываются при рендере/пересчёте, сложность `O(C(n,2) x |tasks|)` при единицах активных тасков незаметна; `is_index_stale` не трогаем.
   Alternatives: кэшировать флаги в `index.json` — лишний формат и инвалидация без выигрыша.

## Risks / Trade-offs

- **Снятие флага прячет DONE-ячейку вместе с вердиктом** → прогресс может вырасти скачком, вердикт при этом на месте и вернётся в учёт при возврате флага. Mitigation: так задумано (нет ответа = ячейки нет); в задачах — явный тест.
- **Строгий приоритет может «голодать» T-002** при долгой череде новичков в T-001 → принято: это и есть требование пользователя.
- **Рематч-fallback может посоветовать BLOCKED-пару** (флаги игнорируются) → принято пользователем осознанно; форма вердикта это позволяет и сейчас.
- **Топ-1 убирает обзор альтернатив** → принято: альтернативы были артефактом смешения READY/BLOCKED.
- **Динамический знаменатель непривычен** (процент падает при появлении ответов) → Mitigation: сценарии в спеке и подпись «осталось N» = числу READY.

## Migration Plan

- Миграции данных нет: `answer_flags.yaml` отсутствует = все BLOCKED = прогресс `—`, рекомендации = рематч-fallback (блок не пустует при ≥ 2 моделях).
- Откат = откат кода + архив спек; данные (вердикты, флаги, индекс) не меняются форматом.
- После кода: `openspec validate --all`, `uv run python tools/test_elo.py`, проверка главной вручную (топ-1, 100%, `—`).
