## Purpose

Сквозной workflow бенчмарка: создание задачи → прогон моделей → судья (вручную) → запись вердикта → leaderboard. Минимальный прогон: 1 задача + 2 модели + 1 вердикт = валидный ELO.

## ADDED Requirements

### Requirement: Шаг 1 — Создание задачи

Пользователь создаёт задачу через skill `benchmark-01-gen-task`. Skill генерирует tasks/T-NNN-<slug>/task.md в диалоге с пользователем.

#### Scenario: Создание задачи

- **WHEN** пользователь вызывает @benchmark-01-gen-task с описанием
- **THEN** skill генерирует task.md в диалоге
- **AND** пользователь подтверждает → файл создаётся

### Requirement: Шаг 2 — Прогон модели

Пользователь запускает модель через skill `benchmark-02-run <model-id>`. Skill готовит промпт: "прочитай task.md, изучи проект (если baseline_commit), напиши ответ в answers/T-NNN/<model-id>.md".

#### Scenario: Прогон модели

- **WHEN** пользователь вызывает @benchmark-02-run claude-sonnet-4.5 для T-001
- **THEN** skill готовит промпт для модели
- **AND** модель пишет answers/T-001/claude-sonnet-4.5.md

#### Scenario: Повтор для других моделей

- **WHEN** пользователь повторяет шаг для gpt-5, gemini-3-pro
- **THEN** создаются answers/T-001/gpt-5.md, answers/T-001/gemini-3-pro.md

### Requirement: Шаг 3 — Судья (вручную)

Пользователь открывает чат с любой LLM (судья). Даёт: task.md + пути к двум файлам ответов. Промпт-шаблон из docs/judge-prompt.md. Судья отвечает в чате: победитель + обоснование + баллы (опц.). Пользователь читает ответ.

#### Scenario: Судья сравнивает два ответа

- **WHEN** пользователь даёт судье task.md + answers/T-001/A.md + answers/T-001/B.md
- **THEN** судья отвечает: "Победитель: Answer 1 (8/10 vs 6/10). Причина: ..."

#### Scenario: Судья не пишет файлы

- **WHEN** судья завершает сравнение
- **THEN** никаких файлов не создаётся автоматически
- **AND** пользователь сам решает, записывать вердикт или нет

### Requirement: Шаг 4 — Запись вердикта

Пользователь открывает веб-UI (localhost:5000), выбирает задачу, модель A, модель B, победителя. Нажимает "Записать". Система создаёт вердикт, пересчитывает ELO, обновляет leaderboard.

#### Scenario: Запись через UI

- **WHEN** пользователь записывает вердикт A > B для T-001
- **THEN** создаётся matchups/T-001/001.json
- **AND** ELO обновляется
- **AND** leaderboard перерисовывается

### Requirement: Шаг 5 — Повтор пар

Пользователь повторяет шаги 3–4 для других пар. Веб-UI подсказывает следующую пару (pairing-algorithm). Количество вердиктов не ограничено.

#### Scenario: Следующая пара

- **WHEN** вердикт A-B записан
- **THEN** веб-UI предлагает следующую пару (например A-C)
- **AND** пользователь повторяет судью + запись

### Requirement: Минимальный прогон

Минимальный валидный прогон: 1 задача + 2 модели + 1 вердикт. Это даёт первый ELO-рейтинг (победитель +16, проигравший -16 от 1200).

#### Scenario: Минимальный прогон

- **WHEN** создана T-001, прогнаны A и B, записан 1 вердикт A > B
- **THEN** A: ELO=1216, B: ELO=1184
- **AND** leaderboard показывает 2 модели

### Requirement: Добавление новой модели

Новая модель добавляется инкрементально: @benchmark-02-run <new-model> для существующей задачи. Затем сравнивается с уже оценёнными моделями (калибровка).

#### Scenario: Новая модель на существующую задачу

- **WHEN** T-001 уже оценена для A, B, C; добавляется D
- **THEN** D прогоняется на T-001 (answers/T-001/D.md)
- **AND** pairing engine предлагает D-A, D-B, D-C (калибровка)

### Requirement: Новая задача

Новая задача создаётся, когда текущая исчерпана (все желаемые модели прогнаны, достаточно вердиктов). Модели стартуют с текущим ELO (переносят рейтинг).

#### Scenario: Переход к новой задаче

- **WHEN** T-001 исчерпана, создаётся T-002
- **THEN** модели не сбрасывают ELO
- **AND** ответы на T-002 пишутся в answers/T-002/
- **AND** вердикты на T-002 продолжают обновлять тот же ELO
