## Context

Текущий бенчмарк построен на 4 категориях задач, кодописательстве, 3 судьях с рубрикатором баллов 0–5, 13 сессий на прогон. Реальных данных нет (только шаблоны) — снос делается с чистого листа. См. proposal.md — Why.

Ограничения:
- Windows, PowerShell, Python 3.10+
- Локальный репозиторий (git), без удалённых сервисов
- Пользователь работает в трёх IDE: Cursor, Devin, OpenCode
- Задачи создаются редко (1 на 2–3 недели), модели добавляются инкрементально
- Судья — любая LLM в любом чате, без автоматизации

## Goals / Non-Goals

**Goals:**
- Минимальный workflow: 1 задача + 2 модели + 1 вердикт = валидный ELO
- Веб-UI для записи вердиктов и просмотра рейтинга (одна страница, всё видно)
- Хранение в git-friendly файлах + генерируемый index.json для быстрого просмотра
- 2 skills (gen-task, run) вместо 6 — судья и leaderboard через веб-сервер
- Архивация моделей без потери истории

**Non-Goals:**
- Многопользовательский доступ (один пользователь, локально)
- Автоматизация судьи (судья — ручной шаг в любом чате)
- Категории задач (один формат: аналитика + код в MD)
- ELO per-category (один глобальный рейтинг)
- Bradley-Terry / Bayesian ELO (классический ELO с адаптивным K)
- Экспорт в форматы кроме HTML
- API для внешних потребителей

## Decisions

### D1: Flask для веб-сервера

**Решение:** Flask, один файл `tools/server.py` (~200 строк).

**Альтернативы:**
- FastAPI — избыточен для одной страницы, требует uvicorn
- Streamlit — тяжёлый, медленный старт, сложный .gitignore
- Чистый http.server — нет шаблонизации, ручной парсинг POST

**Почему Flask:** минимальная зависимость (pip install flask), один файл, встроенный шаблонизатор (Jinja2), тривиальный POST-обработка. Запуск: `python tools/server.py` — одна команда.

### D2: ELO пересчёт — полный, не инкрементальный

**Решение:** При каждом вердикте ELO пересчитывается с нуля из всех вердиктов в хронологическом порядке.

**Альтернативы:**
- Инкрементальное обновление (только дельта от нового вердикта)

**Почему полный пересчёт:** при 10–500 вердиктов пересчёт занимает <100ms. Полный пересчёт гарантирует консистентность (нет накопления ошибок округления, нет рассинхрона при ручном редактировании файлов). Проще код, проще отладка. index.json всегда = функция от matchups/.

### D3: Хранение — файлы + index.json, не SQLite

**Решение:** Source of truth — файлы (models.yaml, tasks/, answers/, matchups/). Кэш — index.json (генерируется).

**Альтернативы:**
- SQLite — быстрые запросы, но бинарник не диффается в git, конфликты слияния нерешаемы
- Один большой JSON — git diff бесполезен при больших ответах, конфликты

**Почему файлы:** git — основная инфраструктура. Каждый вердикт = +1 файл (понятный diff). Каждый ответ = +1 MD (читаемо). index.json — компактный кэш (~10 KB) для просмотра без сервера. При масштабе 1–10 задач × 5–30 моделей это оптимально.

### D4: Судья — без skill, без файлов

**Решение:** Судья работает в любом чате с любой LLM. Пользователь копирует промпт-шаблон из docs/judge-prompt.md, даёт два файла ответов, читает ответ судьи, записывает вердикт через веб-UI.

**Альтернативы:**
- Skill для судьи (как было) — судья пишет файл вердикта автоматически
- MCP-инструмент для судьи

**Почему без skill:** судья может быть любой LLM (не только Devin/Cursor/OpenCode). Промпт-шаблон универсален. Запись вердикта через веб-UI — один клик. Убирает 4 skills (judge, aggregate, status, stale) и всю инфраструктуру изоляции.

### D5: Адаптивный K-factor (40/32/24)

**Решение:** K=40 при <10 играх, K=32 при 10–30, K=24 при >30. K применяется индивидуально к каждой модели в паре.

**Альтернативы:**
- Фиксированный K=32 — проще, но новые модели калибруются медленно
- K=40 для всех — быстрая калибровка, но установившиеся рейтинги флуктуируют

**Почему адаптивный:** стандартная практика (FIDE для шахмат). Новые модели (0–9 игр) получают большие скачки → быстро находят свой уровень. Установившиеся (>30 игр) — стабильные. Индивидуальный K в паре: новая модель vs старая — новая получает K=40, старая K=24.

### D6: Pairing — композитный score

**Решение:** score = 0.5 × undersampled + 0.3 × close_elo + 0.2 × few_games. Пара с наивысшим score предлагается первой.

**Альтернативы:**
- Только близость ELO — игнорирует недооценённые пары
- Только недооценённость — предлагает случайные пары
- Round-robin (строгий порядок) — не адаптируется к новым моделям

**Почему композитный:** баланс между калибровкой (новые модели), информативностью (близкий ELO) и полнотой (мало голосов). Веса 0.5/0.3/0.2 эмпирические — калибровка важнее всего (без неё ELO новой модели = 1200 независимо от реальной силы).

### D7: Архивация — status в models.yaml, не удаление

**Решение:** Архивация = status: archived в models.yaml. ELO замораживается. Файлы ответов и вердиктов не удаляются. Веб-UI фильтрует по status.

**Альтернативы:**
- Удаление модели — потеря истории
- Отдельная папка archived/ — дублирование, сложные пути

**Почему status:** простое поле в YAML, обратимо (разархивация), история сохраняется, git diff минимален (1 строка в models.yaml).

### D8: Skills — 2 вместо 6

**Решение:** `benchmark-01-gen-task` (создать задачу) + `benchmark-02-run` (промпт для модели). Судья, leaderboard, статус, устаревание — через веб-сервер или не нужны.

**Альтернативы:**
- Оставить 6 skills — избыточно, судья не автоматизирован
- 3 skills (добавить judge) — судья всё равно ручной

**Почему 2:** только шаги, требующие LLM-генерации (формулировка задачи, промпт для модели), нужны как skills. Судья — ручной шаг. Leaderboard — веб-сервер. Статус — веб-сервер. Устаревание — не актуально (задачи редкие, baseline опционален).

## Risks / Trade-offs

- **[Flask зависимость]** → один пакет, pip install flask. Если нежелательны внешние зависимости — можно заменить на http.server + ручной шаблонизатор (~300 строк), но потеряем удобство.
- **[Полный пересчёт при каждом вердикте]** → при 500 вердиктах ~100ms. При 5000 (нереалистично) — ~1s. Кэш в index.json компенсирует. Если станет медленно — перейти на инкрементальное обновление.
- **[Судья без автоматизации]** → пользователь может забыть записать вердикт. Нет валидации, что судья действительно сравнивал именно эти ответы. Mitigation: веб-UI показывает, какие пары не оценены.
- **[Ничья редка]** → спецификация требует forced choice, но ничья возможна. При большом % ничьих ELO слабо сходится. Mitigation: промпт судьи подчёркивает "выбери победителя, ничья — только в действительно спорных случаях".
- **[ELO без категорий]** → модель может быть сильна в анализе, слаба в коде. Один рейтинг усредняет. Mitigation: задачи смешанные (аналитика + код), рейтинг отражает общую силу.
- **[index.json в git]** → может рассинхронизироваться при ручном редактировании. Mitigation: сервер проверяет целостность при запуске, пересчитывает если устарел.
- **[Малое число вердиктов]** → при 3 моделях и 3 вердиктах ELO шумный. Mitigation: пользователь может добавить больше вердиктов (повторные сравнения с разными судьями).

## Migration Plan

Миграция не требуется — реальных данных нет (только шаблоны). План:

1. **Phase 0: Очистка** — удалить все старые файлы (кроме models.yaml, register_model.py, .devin/rules, openspec-скиллов). Git commit.
2. **Phase 1: Ядро** — создать tools/elo.py, tools/server.py, tools/generate_html.py, tools/archive_model.py. Ручной тест: 1 задача, 2 фейковых ответа, 1 вердикт.
3. **Phase 2: Структура** — templates, models.yaml доработка, register_model.py доработка.
4. **Phase 3: Skills** — benchmark-01-gen-task, benchmark-02-run.
5. **Phase 4: Документация** — README, AGENTS, docs/*.
6. **Phase 5: OpenSpec** — архивировать старые спеки, применить новые.

**Rollback:** если новая система не подойдёт — git revert коммита Phase 0. Старые файлы восстановятся (но данных всё равно нет).
