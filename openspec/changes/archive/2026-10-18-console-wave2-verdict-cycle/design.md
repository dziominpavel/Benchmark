# Design

## Context

Волна 2 дорожной карты `docs/ui-ux-review.md` (п. 1 «аннулирование из консоли» + п. 2 «форма вердикта»). Мотивация — в `proposal.md`; требования — в дельтах спек (`leaderboard-ui`, `matchup-management`, `elo-engine`, `data-storage`, `static-mirror`).

Текущее состояние, задающее рамки решения:

- Журнал `data/matchups/journal.jsonl` — append-only; единственные точки записи — `elo.record_verdict` и `elo.void_matchup`. `record_verdict` уже возвращает `matchup_id`; `void_matchup` уже пишет tombstone (`void_of`, `reason`), но недоступен из UI и не защищён от повторного аннулирования.
- `data/index.json` — производная проекция (`recalculate` → `generate_index`); сервер читает её через `ensure_index()` (memo в `data_cache` по дайджесту журнала). Индекс уже несёт `elo_history`; счётчики `matchups_summary` знают `voided`, но деталей аннулированных в индексе нет.
- Консоль — Flask + серверные Jinja-шаблоны + небольшой клиентский JS (`validate()` в форме вердикта); фильтры ездят через query-параметры. Механика предзаполнения формы из URL уже есть (`pre_a`, `pre_b`, `pre_task`).
- Зеркало (`export_web.py`) рендерит те же страницы через test client в режиме `read_only()`, собирает страницы истории в один документ и оживляет их `static/js/mirror.js` (клиентская пагинация и фильтры); строки истории извлекаются регуляркой `_HISTORY_ROW_RE` (`<div class="history-item…">…</div>`).
- Бюджеты `tools/test_perf.py` (1000 моделей / 10 000 событий): главная ≤0.5 с typical / ≤1 с peak, страницы ≤1 с.

## Goals / Non-Goals

**Goals:**

- Замкнуть цикл вердикта в браузере: запись → сохранённый контекст → аннулирование (из строки истории и из success-строки) → видимый аудит с причиной и датой.
- Отдавать детали аннулированных через `index.json` (секция `voided_history`), не заставляя консоль читать журнал.
- Не менять формат журнала, порядок реплея и семантику `--check`; не ломать существующие URL/страницы.
- Сохранить корректную деградацию в зеркале: новые контролы записи недоступны, фильтр отображения работает.

**Non-Goals:**

- Фильтры истории по датам/таскам, мастштабирование до 1000 моделей и экспорт — волна 3+ (п. 3, 5, 10 роадмапа).
- Миграции журнала и изменение CLI-контрактов сверх новой опции `--date`.
- Политики, не требуемые спеками: запрет «будущих» дат, лимит длины причины, редактирование вердикта.

## Decisions

### D1. Аннулирование из веб-UI — новый маршрут поверх `void_matchup`, проверки — в движке

- `POST /verdict/void` (`void_verdict_route`): поля `matchup_id`, `reason`, `next`.
- Валидация маршрута: `matchup_id` не пуст; `reason` не пуст (web-UI требует причину, CLI сохраняет прежнее поведение); `next` — только локальный путь (`startswith("/")` и не `"//"`), иначе fallback `/history` (защита от open redirect). Ошибки — `redirect` с `error=`, как у существующих маршрутов; успех — `redirect(next)` с `success=«Вердикт <id> аннулирован»`.
- Проверки «повторное аннулирование» и «нельзя аннулировать tombstone» — в `elo.void_matchup` (перед записью, под journal-lock): цель существует; у цели нет `void_of`; id цели не среди `void_of` существующих событий. `ValueError` — маршрут и CLI показывают текст ошибки.
  - Альтернатива «валидировать только в маршруте» отклонена: CLI остался бы дыркой, а спека требует отказа для обоих путей.
- Форма «Аннулировать» в строке истории: плоская разметка (без вложенных `<div>` — см. D6), скрытая за `<details>`; в форме hidden `matchup_id`, `next` (= `request.full_path` без хвостового `?`), input причины, submit. `read_only()` — блок не рендерится.
- Success-строка после записи: раскрывашка «Отменить» с той же формой (hidden `matchup_id` = только что записанного вердикта), видна лишь когда редирект принёс `matchup_id`.

### D2. `voided_history` в `recalculate` / `generate_index`

- `recalculate` дополнительно собирает `voided_history`: карта `_matchup_id → событие`; для каждого события с `void_of`, чья цель найдена, — запись: `matchup`, `seq`, `task`, `model_a_id`, `model_b_id`, `winner`, `date`, `recorded_at`, `elo_a`/`elo_b` (снэпшот исходного вердикта как записан), `void` = `{reason, date, recorded_at, matchup}` из tombstone. Порядок — по возрастанию `seq` цели; при исторических дублях tombstone на одну цель берётся первый по `seq`; висячая ссылка — существующее предупреждение, запись пропускается.
- `generate_index` кладёт секцию в индекс как есть: `"voided_history": elo_data["voided_history"]`. `build_matchups_summary` не меняется.
- Варианты: (а) сервер читает журнал напрямую — отклонён, это ломает дисциплину «сервер живёт на memo-проекции», (б) хранить только счётчики — не хватает данных для отображения, (в) пересобирать ELO аннулированной записи — отклонён: аудит обязан показывать записанный снэпшот, а не реконструкцию.
- Снэпшот берём из `mu["elo"]` исходного события; для legacy-событий без `elo` — fallback `{before: DEFAULT_ELO, after: DEFAULT_ELO, delta: 0}` (совместимо с `format_elo_history`).

### D3. Дата вердикта

- `record_verdict(..., verdict_date: str | None = None)`: `None` → `date.today()`; иначе валидация «ровно `YYYY-MM-DD`» (regex + `datetime.strptime`) → `ValueError` при невалидной. Имя `verdict_date` — чтобы не перекрывать импортированный `date` внутри функции (иначе `date.today()` внутри станет недоступен).
- CLI: `--date` (help «Дата вердикта YYYY-MM-DD (по умолчанию — сегодня)»), прокидывается в `record_verdict`.
- Веб-форма: `<input type="date" name="date">`; пустое значение → None (сегодня); невалидное / не прошедшее серверную проверку → `redirect` с ошибкой. `--check` не меняется: `date` в проверках целостности не участвует.
- Будущие даты разрешены (спеки их не запрещают); валидируется только формат/календарная корректность.

### D4. Сохранение контекста после записи

- `record_verdict_route` после успеха редиректит на `leaderboard` с параметрами: `success`, `matchup_id` (= `result["matchup_id"]`), `model_a` = победившая модель (для `draw` — прежняя A), `task`, `date` (как отправлена).
- `leaderboard` route: новые переменные `pre_date` (валидная дата из URL, иначе «сегодня»), `today` (для зернового значения input), `saved_matchup_id` (паттерн `T-\d{3,}/\d{3,}`, иначе пусто).
- Шаблон формы: поле даты; кнопка «Поменять A ↔ B» (JS: swap значений + `validate()`); кнопки исхода получают имена моделей (JS обновляет подписи вместе с `validate()`); фокус в `#modelA` при загрузке; `Enter` работает по умолчанию (submit-кнопки).
- Success-алерт расширяется: существующий текст + блок действий («Отменить» — details с формой D1; «Записать ещё» — JS: скрыть алерт, фокус в `#modelB`).
- Альтернатива «сохранять обе модели» отклонена по ревью: минимальная гарантия — победитель в A (следующая пара чаще с его участием), B очищается для быстрого выбора соперника; при `draw` A сохраняется, B очищается.

### D5. Подсказка личных встреч — встроенный JSON, без серверных дозапросов

- Из memo `get_pair_stats()` формируется компактный payload: ключ `"<id_x>|<id_y>"` (ids отсортированы), значение `{"g": games, "x": wins_x, "y": wins_y}`; пары без игр не включаются. Embed: `<script type="application/json" id="pair-hints">…</script>` (escape `</`, как в `build_models_island`).
- Клиентский JS в `validate()` дополнительно обновляет `#pairHint`: для выбранной пары — «Личные встречи: N · счёт по победам A:B · ничьи: D», иначе «не встречались»; имена берутся из текста option (display names), очки маппятся на порядок формы через сортировку ключа.
- Вариант «GET /pair_hint» отклонён: зеркалу запрещены серверные запросы (static-mirror), а подсказка — часть интерактива обеих версий. Подсказка работает и в зеркале (данные в странице) — это отображение, не запись.
- Размер: сейчас пары только с играми (≈595 записей, единицы десятков КБ). На 1000 моделях/10 000 событиях — сотни КБ; сериализация дешёвая (мс, бюджет не задевает), но вес страницы фиксируем как риск волны 3 (п. 5).

### D6. История: объединение лент и рендер аннулированных

- Общий хелпер `render_helpers.merge_history_feed(elo_history, voided_history=())` → единый список по убыванию `seq`: применённые записи без пометок + аннулированные с `voided=True` и `void`/снэпшотом. Используется сервером (`include_voided=1`) и экспортом зеркала (всегда — прячет клиент).
- Роут `/history`: при включённом `include_voided=1` лента = `merge_history_feed(...)`; фильтры по модели/тегам применяются к обеим частям (у записей есть `model_a_id`/`model_b_id`); пагинация по объединённому составу; `history_total` = размер ленты, `history_voided` = число аннулированных (счётчик «Всего записей: N · аннулированных: M»); чекбокс «Показывать аннулированные» в блоке controls; `include_voided` добавляется в `history_params` (пагинация).
- `format_elo_history` расширяется passthrough-полями: `matchup` (нужен кнопке аннулирования), `voided`, `void_str` (маркер «аннулировано {дата} · {причина}»).
- Разметка строки остаётся **плоской** (никаких вложенных `<div>` в `.history-item`): маркер и форма аннулирования — `<span>`/`<form>`/`<input>`/`<button>`; это сохраняет работоспособность `_HISTORY_ROW_RE` в экспорте зеркала. Стили — новые классы `.history-item-voided` (перечёркивание, приглушение) и `.void-form`.
- Альтернатива «отдельный список аннулированных под лентой» отклонена: теряется позиция записи в хронологии, ревью просит аудит на месте.

### D7. Зеркало

- Экспорт `_build_history` переключается на `/history?include_voided=1` (и `&page=k`), ожидаемое число строк — `len(merge_history_feed(...))`; строки получают `data-a`/`data-b` как раньше.
- `mirror.js`: аннулированные строки по умолчанию скрыты; чекбокс «Показывать аннулированные» показывает/прячет их, пересчитывает счётчик (включая «· аннулированных: M» при включении) и клиентскую пагинацию.
- Контролы записи в зеркале: поле даты и кнопка «Поменять A ↔ B» уже внутри `<fieldset disabled>`/`{% if not read_only() %}`; формы аннулирования в истории и в success-строке гейтятся `read_only()`; success-строка в зеркале не рендерится вовсе (POST в зеркале невозможен).

### D8. Стили и тесты

- CSS: `console.css` — стили перечёркивания, маркера, формы аннулирования (в обеих темах, на токенах как соседние элементы).
- Тесты: `tools/test_elo.py` (дата в `record_verdict`/CLI-параметр на уровне функции, запреты повторного аннулирования, состав/порядок/пустота `voided_history`, отсутствие влияния на `elo_history` и счётчики); `tools/test_data_cache.py` (маршруты: запись с `date`, редирект с контекстом и `matchup_id`, `/verdict/void` — успех/пустая причина/чужой id/повтор/`next`-защита, история с `include_voided` и без, счётчик, embed подсказки); зеркало — смоук в `test_export.py` (аннулированные в DOM, disabled-формы); `tools/test_perf.py` — прогон после изменения главной (payload подсказки).

## Risks / Trade-offs

- [Новая защита `void_matchup` отклоняет прежний сценарий «повторно аннулировать»] → это целевое поведение спеки; покрываем тестом, сообщение ошибки человекочитаемое.
- [Исторические журналы с несколькими tombstone на одну цель] → `voided_history` берёт первый по `seq`; `--check`-семантика не меняется.
- [Вес страницы из-за payload подсказки на масштабе 1000 моделей] → компактные ключи, только пары с играми; замер `test_perf.py`; окончательное решение о ленивой выдаче — волна 3 (п. 5).
- [Разметка строки истории ломает извлечение в экспорте] → плоская разметка без вложенных `div` + тест экспорта с аннулированной записью.
- [Open redirect через `next`] → допускаются только локальные пути; прочие игнорируются.
- [XSS через причину аннулирования] → Jinja autoescape (включён Flask по умолчанию) + escape `</` в JSON-острове подсказки.
- [Рассинхрон даты на клиенте и сервере] → серверная валидация формата — источник истины; UI подставляет дату как есть.

## Migration Plan

- Журнал не мигрирует; новых обязательных полей в событиях нет. Первый пересчёт индекса (любая запись/запуск) добавляет `voided_history` автоматически; `python tools/elo.py --check` остаётся зелёным.
- Релиз: CHANGELOG (пользовательский блок + инженерная секция), отметка волны 2 в `docs/ui-ux-review.md`, пересборка статического слепка штатным конвейером (`export_web.py`) после сборки артефактов.
- Откат: revert коммита; `index.json` — производная проекция и восстанавливается пересчётом, данные журнала не затрагиваются.
