## Context

См. `proposal.md` (Why). Факты: `matchups_index` (88 записей × ~318 символов) читают только сводка CLI (`main`), счётчик сервера и несуществующая в коде проверка устаревания (в `is_index_stale` её нет — только дайджест и модели; спека описывала фикцию). `after_matchup` пишется, но не читается никем. `elo_history` нужен целиком (`/history`, страница модели). `matchup` в истории покрыт тестом (`test_elo_history`) — остаётся.

## Goals / Non-Goals

**Goals:**
- Кэш ~80 КБ → ~50 КБ при тех же 88 вердиктах; маржинальная цена вердикта ~0.35 КБ.
- Все потребители (`--check`, сервер, CLI-сводка, тесты) зелёные; старые коммиты кэша продолжают рендериться (fallback), новый формат — после первого пересчёта.

**Non-Goals:**
- Отказ от коммитов кэша (вне скоупа по proposal; пересмотреть, только если дифф продолжит душить после диеты).
- Урезание `elo_history` (нужна целиком двум страницам) и удаление `matchup` (покрыт тестом, identity записей).
- Формат журнала `data/matchups/` не меняется.

## Decisions

1. **Список `matchups_index` → агрегат `matchups_summary`.**
   `build_matchups_index` (пофайловые resolved ids + вызов `load_models_yaml` внутри) заменяется на `build_matchups_summary(matchups, applied, voided, skipped)` → `{total, applied, voided, tombstone, skipped}` (подсчёт без разбора моделей). Почему агрегат, а не удаление: потребителям нужны только числа (счётчик сервера, сводка CLI); полный список дублирует файлы журнала, читаемые напрямую при нужде.
2. **`after_matchup` удаляется из `recalculate` (+ докстринг).**
   Мёртвое поле: одна запись, ноль чтений. `matchup` остаётся.
3. **`is_index_stale` не меняется.**
   Проверки дайджеста и моделей уже покрывают состав журнала; счётной проверки в коде не было (спека врала — дельта это чинит). Дополнительно: отсутствие `matchups_summary` устареванием НЕ считается — старый кэш валиден до первого пересчёта.
4. **Совместимость назад через fallback, а не миграцию.**
   Сервер: `summary.total`, иначе `len(matchups_index)` (старый кэш). Отдельного скрипта миграции нет — формат обновляется лениво первым же пересчётом; старые коммиты остаются читаемыми историей git.
5. **Числа в спеку — замером после реализации, не прогнозом.**
   ~50 КБ при 88 и ~0.35 КБ/вердикт — из прямого замера; сценарий «100 вердиктов → ~55 КБ» согласован с маржинальной ценой.

## Risks / Trade-offs

- [Risk] Сторонний читатель `matchups_index` вне `tools/` (документация, скрипты пользователя). Mitigation: grep по репо перед удалением; в спеках и docs секция больше не упоминается (проверяется в tasks).
- [Risk] Потеря подетального `status` в кэше (tombstone/voided видны только в журнале). Mitigation: агрегат хранит счётчики; детали и так только в файлах — кэш их дублировал.
- [Trade-off] Прогноз ~180 КБ на 500 вердиктов — всё ещё рост, но линейный с малой константой и только от истории, реально нужной UI. Дальше — только отказ от коммитов кэша (вне скоупа).
