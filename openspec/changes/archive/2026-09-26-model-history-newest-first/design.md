## Context

`get_model_detail()` в `tools/render_helpers.py` собирает данные страницы модели
из `data/index.json["elo_history"]` одним проходом по отсортированной по `seq`
последовательности `mine`. Из неё образуются два независимых результата:

```
mine (seq ASC)
   |-- points[]   --> build_elo_svg()   --> «Динамика ELO»   (нужна хронология)
   |-- history[]  --> MODEL_TEMPLATE    --> «История матчей»  (нужен reverse)
   |-- h2h{}      --> H2H-таблица       (порядок не важен, сортируется отдельно)
```

Ограничения, из которых исходит дизайн (мотивация — в `proposal.md`):

- `points` кормит SVG-график, который по `leaderboard-ui` SHALL строиться
  в порядке `seq`; инвертировать исходную последовательность нельзя.
- `history` потребляет ровно один потребитель — цикл
  `{% for h in detail.history %}` в `MODEL_TEMPLATE`. Других читателей
  `detail.history` в `tools/server.py` нет.
- Порядок в `history` не влияет на содержимое строк: `before`, `after`, `delta`
  и исход вычисляются для каждой записи независимо, кумулятивных вычислений
  из списка нет.
- Страница `/history` уже показывает записи в обратном порядке
  (`list(reversed(...))` в `server.py`), то есть выбранное поведение
  приводит два окна истории к одному порядку.

## Goals / Non-Goals

**Goals:**

- Строки блока «История матчей» на `/model/<id>` идут в обратном
  хронологическом порядке — новые сверху.
- SVG-график «Динамика ELO» остаётся хронологическим (старые слева).
- Одно место правки: агрегация в `render_helpers.py`; шаблон и роут не трогаем.

**Non-Goals:**

- Пагинация или виртуализация длинной истории (список показывается целиком,
  как и сейчас).
- Изменение `elo_history` в `index.json`, журнала вердиктов или ELO-расчёта.
- Изменение страницы `/history` — она уже в обратном порядке.
- Интерактивная сортировка по клику на заголовки колонок.

## Decisions

### 1. Ключ сортировки — обратный порядок `seq`, а не строковая сортировка по `recorded_at`

**Решение:** инвертировать последовательность, собранную в порядке `seq`.

`seq`, `date` и `recorded_at` на текущих данных монотонны (проверено: все 195
записей отсортированы одновременно по всем трём полям), поэтому обратный
`seq` и есть сортировка по дате в обратном порядке.

Альтернативы отклонены:

- *Строковая сортировка по `recorded_at` DESC* — в данных смешаны таймзоны
  (`+00:00` и `+03:00`), лексикографический порядок совпадает с хронологическим
  только случайно; на соседних записях одного дня с разными смещениями
  дал бы неверный порядок.
- *Сортировка только по `date` DESC* — `date` имеет гранулярность дня,
  12 из 13 дней содержат по нескольку матчей, потребовались бы тай-брейки.
- *Числовая сортировка `(-seq)`* — эквивалентна развороту, но требует, чтобы
  `seq` был числом и присутствовал у каждой записи; разворот от этого
  не зависит (строится на фактическом порядке `elo_history`).

### 2. Инвертировать только `history`, сохраняя `mine` в исходном порядке

**Решение:** после цикла сбора выполнить разворот списка, идущего в таблицу
(`history.reverse()` / `list(reversed(history))`), и вернуть его под ключом
`history`. `mine`, `points` и `h2h` остаются как есть.

Почему не другие варианты:

- *`mine.reverse()` до цикла* — молча ломает график: точки пойдут справа
  налево, min/max и подпись «текущий» привяжутся к неверным точкам. Это
  единственный скрытый провал в этой правке.
- *Сортировка в шаблоне* — держит логику в данных, шаблон продолжает
  только итерировать; сортировка в Jinja-цикле неудобна и не тестируется.
- *Отдельный ключ в `format_elo_history`* — тот же рендер-хелпер, но он
  принимает уже нарезанный кусок для `/history`, который перевёрнут раньше;
  правка там не достигла бы страницы модели.

### 3. Порядок в `history` не несёт данных — правка без контрактных последствий

`history[i]` не используется ни для какого вычисления после сборки: строки
самодостаточны (`before`/`after`/`delta`/исход зафиксированы на момент
матча). Поэтому инверсия не меняет ни одной цифры на странице — меняется
только порядок строк.

### 4. Докстринг обновляется синхронно с кодом

Докстринг `get_model_detail()` сейчас обещает «history … в порядке `seq`».
Расхождение докстринга и поведения — ровно тот вид бага, который эта правка
и исправляет, поэтому описание меняется в том же изменении: `history` — в
обратном порядке, `points` — в хронологическом.

## Risks / Trade-offs

- [Кто-то «упростит» правку, инвертировав `mine`, и сломает график] →
  в delta-спеке отдельный сценарий «График сохраняет хронологический порядок»
  фиксирует разнонаправленность двух списков; в коде — комментарий у места
  инверсии; в задачи включена ручная проверка графика.
- [`seq` может не совпадать с календарной датой, если появятся легаси-вердикты
  без `seq` (в `matchup_sort_key` они идут до событий с `seq`)] → на текущих
  данных таких записей нет (0 из 195); семантический источник истины — порядок
  реплея, а не календарь, поэтому обратный `seq` остаётся корректным и для них.
- [Несколько матчей в один день: какие из них «выше»] → разворот стабилен,
  внутри дня сохраняется обратный порядок применения (последний матч дня —
  выше всех остальных матчей того же дня). Это соответствует ожиданию
  «последние сверху».
- [Правка в общем хелпере затронет и другие страницы] → проверено:
  `detail.history` читает только `MODEL_TEMPLATE`; на `/stats` и `/history`
  используются другие функции.
- [Длинная история (сотни строк) — новые матчи вверху означают, что старые
  уходят вниз за предел экрана] → это осознанный обмен, идентичный поведению
  `/history`; пагинация в non-goals.

## Migration Plan

Миграция не требуется: данные (`index.json`, журнал вердиктов) не меняются,
изменение проявляется только при следующем рендере страницы модели. Откат —
реверт одного изменения в `render_helpers.py` вместе с правкой спеки.
