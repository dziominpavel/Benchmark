# Design: settings-and-task-progress

## Context

См. proposal.md — Why. Ключевые факты о текущем состоянии:

- Форма вердикта пишет всегда в `general` (`task=DEFAULT_TASK`,
  `tools/server.py`), поля таска в UI нет.
- `record_verdict` уже принимает `task`, валидирует `[A-Za-z0-9_-]+`
  и сам создаёт `matchups/<task>/` — движок менять не нужно.
- `get_pair_stats` уже умеет пропускать tombstone- и аннулированные
  вердикты и резолвить id — логику переиспользуем для покрытия.
- Активность моделей определяется `status` в `models.yaml`
  (`is_model_active`).
- PyYAML уже зависимость проекта (`load_models_yaml`).

## Goals / Non-Goals

**Goals:**

- Единая страница `/settings` как точка входа для действий управления.
- Реестр активности тасков + `current_task` в `settings.yaml`.
- Поле таска в форме вердикта с дефолтом `current_task`.
- Честная метрика покрытия «все активные модели × все активные таски»,
  устойчивая к повторам и мусорным таскам.

**Non-Goals:**

- Статичный экспорт `generate_html.py` не меняется (прогресс — только
  на серверной странице).
- CLI `record_verdict.py --task` не меняется.
- Рекомендательный алгоритм (`get_recommendations`) не учитывает таски —
  остаётся как есть (рекомендует пары по общему числу игр).

## Decisions

### 1. Активные таски задаются списком со статусами, а не числом

Изначальная идея — вручную вводить «всего тасков N». Отклонено: число не
называет, **какие** таски активны, а требование «учитывать только активные»
появилось позже. Вместо числа — реестр статусов в `settings.yaml`
(по аналогии со `status` моделей в `models.yaml`):

```yaml
current_task: general
tasks:
  general: active
  T-001: active
  typo-dir: inactive
```

`N = число тасков со статусом active`. UI `/settings` показывает все
известные таски с чекбоксом «активна» и радио «текущая» — фактически
это тот же ввод «1 или 2», только явный.

**Альтернатива**: число N + отдельный список исключений — два места
правки, рассинхрон смысла. **Альтернатива**: статус в `task.md` front
matter — не покрывает таски, существующие только в `matchups/`
(`general`, опечатки), и разносит состояние по двум файлам.

### 2. Множество известных тасков — объединение трёх источников

`known_tasks = директории matchups/ ∪ id из tasks/T-NNN-* ∪ ключи
settings.yaml.tasks`. Так в список попадают и `general` (нет папки в
`tasks/`), и опечатки в `matchups/` (их можно сразу пометить inactive),
и будущие таски. Извлечение id из `tasks/` — тем же правилом, что
`collect_tasks_info` (префикс `T-NNN`).

### 3. Дефолт для неизвестной таски — active

Таска без записи в `settings.yaml` считается активной. Обратный дефолт
(inactive) безопаснее против опечаток, но молча прячет реальный прогресс
новой таски — пользователь не поймёт, почему процент не растёт. Опечатка
заметна сразу (новая строка в настройках) и гасится одним чекбоксом.

### 4. Прогресс — покрытие ячеек (таск × пара), не счёт вердиктов

```
cells      = { (task, frozenset(a, b)) | вердикт не аннулирован,
               task активен, a и b активны }
Прогресс   = |cells| / (N_active_tasks * C(N_active_models, 2)) * 100,
             кап 100%
```

Это в точности «пара закрыла таск ≥1 игрой»: повторы в ячейке не
засчитываются, игра в «чужом»/неактивном таске не засчитывается.
Эквивалентно `Σ min(разных активных тасков пары, N) / (N·C(A,2))`, но
фильтрация по именам тасков прозрачнее и дешевле — один проход по
`load_matchups()` (как `get_pair_stats`).

Расчёт — при каждом рендере главной (matchups уже грузятся для
рекомендаций); в `index.json` не кэшируется, т.к. зависит от
`settings.yaml`, который не входит в `matchups_digest`.

### 5. Размещение кода

- `elo.py`: `load_settings()`, `save_settings()`, `known_tasks()`,
  `get_coverage()` — рядом с `load_models_yaml`/`load_matchups`,
  покрывается тестами `test_elo.py`-стилем.
- `server.py`: роуты `GET/POST /settings`, шаблон `SETTINGS_TEMPLATE`,
  поле таска в `INDEX_TEMPLATE` (`<input name="task" list="task-list">` +
  `<datalist>`), вызов `get_coverage()` в `leaderboard()`.

### 6. current_task — только из активных

В форме настроек радио «текущая» доступно только для активных строк;
при сохранении `current_task`, указывающий на неактивную/неизвестную
таску, отклоняется или сбрасывается на `general`. При рендере формы
вердикта: если сохранённый `current_task` стал неактивным — подставляется
`general`.

## Risks / Trade-offs

- **[Опечатка в поле таска формы создаёт новую папку в `matchups/`]** →
  валидация `[A-Za-z0-9_-]+` в `record_verdict` + datalist подсказывает
  существующие; новая таска появится в настройках и гасится чекбоксом.
- **[Деноминатор растёт при добавлении модели]** → это честное поведение:
  прогресс падает, показывая объём оставшейся работы. Задокументировано
  в спеке (пересчёт обеих частей при архивации).
- **[Настройки правятся и руками]** → `load_settings` терпимо парсит:
  отсутствующие/битые поля → дефолты, без падения сервера.
- **[Старая раскладка «всё в general»]** → `general` остаётся обычной
  активной таской, её 61 вердикт продолжает закрывать ячейки.

## Migration Plan

1. Создать `settings.yaml` можно либо руками, либо первым сохранением
   на `/settings`. До этого работают дефолты (всё активно,
   `current_task: general`) — поведение формы совместимо со старым
   (вердикт в `general`).
2. Откат — удаление `settings.yaml` и реверт кода; вердикты не
   затрагиваются.

## Open Questions

- Точные подписи в UI («Прогресс: 33% · закрыто 61 из 182» vs. просто
  процент) — выберется при реализации, на спеки не влияет.
