# leaderboard-ui Specification

## Purpose
Веб-интерфейс leaderboard на локальном Flask-сервере (`tools/server.py`):
таблица рейтинга, блок рекомендаций пар, форма записи вердикта в корзину
`general`, страница добавления модели, история ELO. Плюс статичный экспорт
`leaderboard.html` (`tools/generate_html.py`, только чтение).

## Requirements

### Requirement: Локальный веб-сервер

Система SHALL запускаться командой `python tools/server.py` (или `start.bat`)
и слушать `http://localhost:<port>`. При занятом порту 5000 система SHALL
выбрать следующий свободный (5001, 5002, … до 10 попыток) через `find_free_port`
и вывести фактический URL. `start.bat` открывает фиксированный
`http://localhost:5000`, поэтому при занятом порте адрес из консоли точнее.

#### Scenario: Запуск сервера

- **WHEN** пользователь выполняет `python tools/server.py`
- **THEN** сервер слушает 127.0.0.1 на свободном порту от 5000
- **AND** выводит URL вида `http://localhost:5000`

### Requirement: Таблица рейтинга (сервер)

Главная страница SHALL показывать таблицу с колонками: `#`, `Модель`, `ELO`,
`Побед`, `Поражений`, `Ничьих`, `Всего`, отсортированную по ELO по убыванию.
Колонки `Провайдер` в серверной таблице НЕТ (она есть только в статичном экспорте).
Строка статистики SHALL показывать «Моделей: N · Вердиктов: M · Обновлено: D».

#### Scenario: Отображение рейтинга

- **WHEN** пользователь открывает страницу сервера
- **THEN** видит таблицу всех моделей из `index.json` по убыванию ELO
- **AND** ELO-бейдж: зелёный при ≥1300, жёлтый при ≥1150, красный ниже

#### Scenario: Нет моделей

- **WHEN** в реестре нет моделей
- **THEN** таблица заменяется пустым состоянием «Нет моделей. Нажмите «+ Добавить модель»…»

#### Scenario: Меньше двух моделей для вердикта

- **WHEN** моделей меньше 2
- **THEN** форма вердикта заменяется состоянием «Нужно минимум 2 модели…»

### Requirement: Архивные модели (фактическое поведение)

Серверная таблица MUST NOT фильтровать архивные модели: отдельного флага
«показывать архивные» и серой подсветки на сервере нет. Переключатель архивных
есть ТОЛЬКО в статичном `leaderboard.html` (скрыты по умолчанию, показ по чекбоксу).

#### Scenario: Архивная модель на сервере

- **WHEN** модель C имеет `status: archived`
- **THEN** сервер показывает её наравне с active-моделями
- **AND** это фактическое поведение MVP

### Requirement: Форма записи вердикта

Форма SHALL содержать два dropdown (Модель A, Модель B, отсортированы по имени)
и три кнопки отправки: «Победила A» (`winner=a`), «Победила B» (`winner=b`),
«Ничья» (`winner=draw`). Кнопки SHALL быть заблокированы, пока не выбраны обе
модели и A ≠ B (JS-валидация `validate()`). Выбора задачи в форме нет — вердикт
всегда пишется в корзину `general`.

#### Scenario: Заполнение формы

- **WHEN** пользователь выбирает A, B (A ≠ B) и нажимает «Победила A»
- **THEN** POST /verdict создаёт `matchups/general/NNN.json`, пересчитывает ELO
- **AND** страница перезагружается с сообщением «Записано: A vs B → A»

#### Scenario: Валидация в UI

- **WHEN** выбраны одинаковые модели или одна не выбрана
- **THEN** все три кнопки заблокированы

### Requirement: Блок рекомендаций

Блок «Рекомендуемые модели к прогону» SHALL показывать одну пару
(первую из топ-3 pairing-algorithm: имя, ELO, причина) с кнопкой
«Прогнать», подставляющей пару в форму вердикта и прокручивающей
к ней. Остальные пары SHALL листаться кнопкой «→» (счётчик «N / M»,
листание по кругу через `showRec`/`nextRec`). Если несравнённых пар
нет и моделей ≥ 2 — показывается плашка «Все пары уже прогнаны…».

#### Scenario: Отображение рекомендации

- **WHEN** есть несравнённые пары
- **THEN** блок показывает первую пару топ-3 с причиной
- **AND** кнопка «→» показывает следующую, кнопка «Прогнать» заполняет dropdowns формы

### Requirement: История ELO

Страница SHALL показывать последние 20 записей `elo_history` (новые сверху):
имя модели, имя соперника, ELO до вердикта, ELO после вердикта, дельту
(+N зелёным / −N красным / ±0 серым) и дату. Каждая запись SHALL соответствовать
одной стороне одного вердикта: `model` — модель, `opponent` — соперник,
`elo_before` — ELO до, `elo` — ELO после, `delta` — изменение.

#### Scenario: История после вердикта

- **WHEN** записан вердикт A > B
- **THEN** сверху истории две записи:
  - A vs B: ELO 1200 → 1220 (+20)
  - B vs A: ELO 1200 → 1180 (−20)
- **AND** обе записи содержат дату вердикта

#### Scenario: Ручная запись через UI

- **WHEN** пользователь ввёл вердикт через веб-форму
- **THEN** в истории появляется запись с реальными id модели и соперника
- **AND** для каждой стороны видны ELO до, ELO после и дельта

### Requirement: Страница добавления модели

Страница `/add` SHALL содержать форму с единственным полем «Название модели»
и список уже добавленных (имя, ELO, игры). POST /add_model генерирует slug
из названия (`slugify`: нижний регистр, дефисы; пусто → `model-N`; занят →
суффикс `-2`, `-3`…), добавляет модель со `status: active`, сортирует реестр
по id, сохраняет `models.yaml` и пересчитывает `index.json`.

#### Scenario: Добавление модели

- **WHEN** пользователь вводит «GPT-4o» и нажимает «Добавить»
- **THEN** в реестре появляется id `gpt-4o` со стартовым ELO 1200
- **AND** страница показывает успех «Модель «GPT-4o» добавлена. Стартовый ELO: 1200»

#### Scenario: Пустое название

- **WHEN** поле имени пусто
- **THEN** сервер отклоняет с ошибкой «Введите название модели»

### Requirement: Статичный экспорт HTML

Скрипт `tools/generate_html.py` SHALL генерировать `leaderboard.html` из
`index.json` (только чтение, без формы). Таблица экспорта, в отличие от серверной,
SHALL содержать колонку `Провайдер`, серую подсветку архивных строк и чекбокс
«Показывать архивные» (по умолчанию скрыты). При отсутствии `index.json` скрипт
SHALL завершаться с ошибкой и подсказкой запустить `python tools/elo.py`.

#### Scenario: Генерация статичного HTML

- **WHEN** пользователь выполняет `python tools/generate_html.py`
- **THEN** создаётся `leaderboard.html`, открываемый через `file://`
- **AND** внизу пометка про запуск сервера для записи вердиктов
