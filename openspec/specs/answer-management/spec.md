# answer-management Specification

## Purpose
Хранение слотов ответов для текущего судейства. Skills прогонов пишут
фиксированные файлы `modelA.md` / `modelB.md` без поля `model` в шапке
(слот определяется именем файла); тексты ответов моделей не входят в git:
для судейства используются два транзитных слота, а ручные копии могут лежать
локально. В проекте ведётся только ручной учёт наличия (см. `answer-coverage`).

## Requirements

### Requirement: Формат ответа

Каждый ответ, поданный на судейство, SHALL храниться в проекте только как транзитный слот `data/answers/<task-id>/modelA.md` либо `data/answers/<task-id>/modelB.md`. Файлы `<model-id>.md` MAY существовать локально для ручного архива, но система MUST NOT читать их как источник ответа, и они MUST NOT коммититься: для судейства текст копируется в слот. В проекте ведётся только ручной учёт наличия (см. `answer-coverage`). Файл слота SHALL содержать YAML front matter с полями `task` и `date`; поле `model` MUST NOT присутствовать. Идентичность слота SHALL определяться только именем файла (`modelA` / `modelB`), содержимое шапки авторитетом не является и судьёй игнорируется.

#### Scenario: Ответ skill прогона

- **WHEN** `@benchmark-run-a T-001` или `@benchmark-run-b T-001` завершает работу
- **THEN** создаётся `data/answers/T-001/modelA.md` либо `data/answers/T-001/modelB.md` своего слота
- **AND** front matter содержит только `{task: "T-001", date: "YYYY-MM-DD"}` без поля `model`
- **AND** `data/answers/T-001/slots.json` не создаётся

#### Scenario: Ответ произвольной модели вручную

- **WHEN** модель с id из `data/models.yaml` отвечает на T-001
- **THEN** текст ответа MAY храниться локально в `data/answers/T-001/<model-id>.md` (каталог игнорируется git) или вне проекта
- **AND** для судейства копируются только два слота `modelA.md` / `modelB.md`
- **AND** координатор отмечает наличие ответа в ручном учёте (см. `answer-coverage`)

#### Scenario: Старый файл с полем model внутри

- **WHEN** на судейство подан файл, внутри которого осталось поле `model` (наследие формата до изменения)
- **THEN** судья игнорирует это поле и определяет слот только по имени файла и порядку вставки (Answer 1 = A, Answer 2 = B)

### Requirement: Содержание ответа

Тело ответа SHALL содержать разделы: `Анализ`, `Находки` (каждая — файл:строка,
критичность, описание, пример входных данных, исправление в блоке ```),
`Граничные случаи (проверено, не баг)`, `Дополнительные находки`.
Код SHALL быть в ограждённых блоках с языком (например ```kotlin).

#### Scenario: Ответ с кодом

- **WHEN** модель предлагает исправление бага
- **THEN** ответ содержит блок ```kotlin с исправленным кодом
- **AND** текстовое описание проблемы, пример и критичность

#### Scenario: Ответ с анализом без кода

- **WHEN** задача требует только анализ
- **THEN** ответ содержит текстовый анализ с заголовками
- **AND** код может отсутствовать

### Requirement: Уникальность ответа

На одну задачу один слот/модель SHALL иметь один файл ответа. Повторный прогон
SHALL перезаписывать файл; вердикты со старым ответом сохраняются, ELO
пересчитывается при следующем обновлении (связи вердикт↔версия ответа нет).

#### Scenario: Повторный прогон

- **WHEN** `@benchmark-run-a T-001` запускается повторно
- **THEN** `data/answers/T-001/modelA.md` перезаписывается
- **AND** существующие вердикты остаются в силе

### Requirement: Шаблон ответа

Файл `data/answers/_TEMPLATE.md` SHALL содержать пустой шаблон с front matter из полей `task` и `date` без поля `model`, и секциями (Анализ, Находки с примером структуры, План, Дополнительные находки). Skills прогонов используют собственный (более детальный) формат из SKILL.md, совместимый с шаблоном по front matter без `model`.

#### Scenario: Ручной ответ из шаблона

- **WHEN** координатор готовит слот вручную из шаблона
- **THEN** структура берётся из `data/answers/_TEMPLATE.md`
- **AND** поле `model` в шапке отсутствует
- **AND** секции заполняются находками

### Requirement: Проверка наличия ответа (фактическое поведение)

Проверку наличия двух слотов SHALL выполнять skill `benchmark-judge` и ручной путь по `docs/judge-prompt.md` до начала оценки: проверяются существование `modelA.md` / `modelB.md`, непустота тела и совпадение `task` с текущей задачей. Поле `model` внутри файла MUST NOT проверяться и MUST NOT блокировать судейство. Веб-сервер при записи вердикта наличие ответов MUST NOT проверять — валидация ограничена реестром моделей (см. matchup-management).

#### Scenario: Судья без ответа

- **WHEN** `@benchmark-judge T-001` вызван, но `modelB.md` отсутствует
- **THEN** skill сообщает какой прогон запустить и останавливается

#### Scenario: Вердикт веб-формы без ответов

- **WHEN** у моделей нет ответов, но обе есть в реестре
- **THEN** сервер записывает вердикт без ошибок

#### Scenario: Расхождение шапки со слотом не блокирует

- **WHEN** файл `modelA.md` содержит внутри `model: modelB` или реальный `id` (ошибка/наследие)
- **THEN** судья продолжает оценку как слот A и не запрашивает корректную пару по этой причине

### Requirement: Анонимность ответа участника

Участник skill-прогона MUST NOT записывать свой реальный `model-id` ни в имя файла (всегда строго `modelA.md` / `modelB.md` своего слота), ни в front matter, ни в тело ответа, ни во вспомогательные файлы рядом с ответом (например, `slots.json`). Поле `model` во front matter MUST NOT присутствовать. Связь слота с реальным `id` устанавливается координатором позже, при записи вердикта, вне проекта.

#### Scenario: Ответ участника A

- **WHEN** `@benchmark-run-a T-001` завершает работу
- **THEN** создаётся `data/answers/T-001/modelA.md`
- **AND** файл не содержит поля `model` и реального `id` нигде
- **AND** в `data/answers/T-001/` не создаётся `slots.json`
- **AND** участник не знает и не записывает реальный `id`

#### Scenario: Ответ участника B

- **WHEN** `@benchmark-run-b T-001` завершает работу
- **THEN** создаётся `data/answers/T-001/modelB.md`
- **AND** файл не содержит поля `model` и реального `id` нигде
- **AND** файл `data/answers/T-001/slots.json` отсутствует
