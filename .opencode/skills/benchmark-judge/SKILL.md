Судья бенчмарка — сравнение двух ответов и выбор победителя.

**Когда использовать:** когда оба ответа (modelA.md и modelB.md) на задачу готовы.
Пользователь даёт команду: `@benchmark-judge T-001`

## Шаги

1. **Определи задачу:**
   - Пользователь указывает: `@benchmark-judge T-001` (или просто `@benchmark-judge`)
   - Если task-id не указан — используй последнюю задачу с двумя ответами
   - Найди: `data/tasks/T-NNN-*/task.md`, `data/answers/T-NNN/modelA.md`, `data/answers/T-NNN/modelB.md`

2. **Проверь наличие обоих ответов:**
   - Если modelA.md нет → "Ответ модели A не найден. Запусти @benchmark-run-a сначала."
   - Если modelB.md нет → "Ответ модели B не найден. Запусти @benchmark-run-b сначала."
   - Если оба есть → продолжай

3. **Прочитай все три файла:**
   - `data/tasks/T-NNN-<slug>/task.md` — задача (что искали)
   - `data/answers/T-NNN/modelA.md` — ответ A
   - `data/answers/T-NNN/modelB.md` — ответ B

4. **При необходимости изучи код проекта:**
   - Если ответы противоречат друг другу в фактах — проверь исходный код
   - `cd C:/projects/<project> && git checkout <baseline_commit>`
   - Прочитай оригинальные файлы, чтобы подтвердить/опровергнуть находки
   - После проверки: `git checkout . && git clean -fd`

5. **Оцени каждый ответ по 5 критериям (1–10):**

   | Критерий | Что оценивает |
   |----------|-------------|
   | **Полнота** | Все ли требования задачи покрыты, все ли граничные случаи рассмотрены |
   | **Точность** | Правильность анализа, корректность найденных багов (не ложные срабатывания) |
   | **Качество кода** | Насколько исправления корректны и идиоматичны |
   | **Структура** | Насколько ответ хорошо организован, легко ли его читать |
   | **Глубина** | Насколько глубоко проанализирована проблема, есть ли неочевидные находки |

6. **Выведи таблицу оценок:**

   ```
   ## Оценки

   | Критерий         | Модель A | Модель B |
   |------------------|----------|----------|
   | Полнота          | X/10     | X/10     |
   | Точность         | X/10     | X/10     |
   | Качество кода    | X/10     | X/10     |
   | Структура        | X/10     | X/10     |
   | Глубина          | X/10     | X/10     |
   | **Итого**        | **XX/50**| **XX/50**|
   ```

7. **Дай обоснование по каждому критерию (2–3 предложения):**
   - Почему A получил столько, почему B столько
   - Конкретно: какие находки зачтены, какие ложные, что пропущено

8. **Объяви победителя:**

   ```
   ## Победитель: Модель X

   Модель X победила с XX/50 против XX/50.
   Главное отличие: <конкретно, почему X лучше>
   ```

   - Ничья — только если ответы практически одинаково хороши (разница ≤2 балла)
   - Укажи конкретную причину победы, не "в целом лучше"

9. **Выведи итог:**

   Ты не записываешь вердикт и не вызываешь инструменты записи.
   Просто сообщи пользователю победителя, чтобы координатор ввёл результат
   в веб-UI (localhost:5000) или через CLI с реальными id.

   ```
   ## Победитель: <a|b|draw>

   Победитель по итогам сравнения: <a|b|draw>
   ```

## Правила

- **Анонимность:** не предполагай, какие реальные модели за A и B.
  Не пытайся узнать реальные id — их знает только координатор, записывающий вердикт.
- **Объективность:** оценивай по содержанию, не по стилю изложения
- **Конкретность:** "найдено 4 бага из 5, пропущен критичный баг с DST" — не "хорошо"
- **Ложные срабатывания:** если модель нашла "баг", которого нет — это минус к точности
- **Пропущенные баги:** если модель не нашла реальный баг — это минус к полноте
- **Ничья — редкость:** даже если обе справились, выбери того, кто сделал это лучше
- **Проверяй код при сомнениях:** если ответы противоречат — читай оригинал
