Координатор батч-судейства — прогоняет N пар (по умолчанию 10). Вердикты НЕ записывает — их вбивает пользователь через UI кнопкой «Прогнать» на карточке топ-1 строго по очереди 1..N. Никаких ссылок с предзаполнением, никаких dropdown-поисков вручную.

**Когда использовать:** команда `@benchmark-batch-judge [N] [T-NNN]`. Без N — 10.

## Шаг 0. Определи TASK (один на всю пачку, без смешивания)

- Явный `T-NNN` имеет приоритет.
- Без него — `current_task` из `data/settings.yaml` (смешивать T-001+T-002 запрещено).
- Дальше работай только с этим TASK.

## Шаг 1. Снапшот, карта файлов, заморозка N пар

- Зафиксируй `git status --short` и `git rev-parse HEAD` Benchmark (проект не меняй).
- Источник истины — файлы, НЕ флаги (`get_recommendations` в `tools/server.py:339` считает READY только по `answer_flags.yaml` + отсутствию вердикта и файлов не видит).
- Построй карту файлов скриптом (не одним чтением директории — листинг режется постранично): для каждого `id → name` из `models.yaml` проверь `data/answers/<TASK>/<name>/` на наличие хотя бы одного `*.md`. Имя внутри (`modelA.md` ИЛИ `modelB.md`) — артефакт прошлого слота, значения не имеет.
- Ловушка дрейфа имён: если флаг `true`, а директории с точным `name` нет — ищи похожее имя (пример: `models.yaml` говорит `Codex GPT-5.6-Terra High 09-2026`, а на диске `Codex GPT-5.6-Terra 09-2026`). Проверь front matter файла (`task: T-XXX`), при совпадении переименуй директорию под `models.yaml` (каталог игнорируется гитом, в `git status` не светится) и зафиксируй это в отчёте.
- Аудит: сравни `answer_flags.yaml[TASK]` с картой файлов, перечисли несовпадения. Флаги руками не чини без просьбы — дальше иди по файлам.
- Заморозь первые N пар С ОБОИМИ файлами из `get_recommendations(generate_index(), top_n=K)`: старт `K = N×3`, удваивай до max 500, пока валидных < N. Фильтр `recommended_task == TASK`, порядок рекомендаций сохраняй. Если валидных < N и при max — СТОП с явным сообщением.
- Сообщи стартовую позицию UI (обычно 1; если верх занят несуждаемыми — с какой позиции стартует пачка).

## Шаг 2. Анонимизация (обязательно)

- Скопируй каждую пару в `C:\Users\Dziom\AppData\Local\Temp\opencode\batch-<TASK>-<N>\pair<i>\` + `meta.txt` (`pair<i>: A=<id> B=<id> task=<TASK>`).
- Строго по сторонам: файл стороны A → `modelA.md`, стороны B → `modelB.md`, НЕЗАВИСИМО от исходного имени.
- Судьям давай ТОЛЬКО эти пути — никогда оригиналы с именами моделей.

## Шаг 3. Параллельное судейство с нуля

- Запусти N суб-агентов параллельно, каждый строго по `benchmark-judge`: только `task.md` + свои `modelA.md/modelB.md`.
- Каждый судья работает с нуля: запрети ему `index.json`, `models.yaml`, `matchups/`, чужие пары, ELO, прошлые вердикты и счета других пар, выяснение реальных ID, запись в репозиторий, `record_verdict`. На предыдущие оценки пар он не ориентируется.
- Каждый: своя копия baseline (`git clone --no-local --no-checkout`, checkout только там, проверить полный HEAD), шкала задачи (T-001 — /50, ничья при разнице <2; T-002 — рубрика /100 из task.md).
- Собери: победитель `a|b|draw`, счёт, 3–6 пунктов с `файл:строка`.

## Шаг 4. Порядок под кнопку «Прогнать» (симуляция траектории ELO)

- Пользователь вбивает только через кнопку «Прогнать» на карточке топ-1 и выбирает победителя из списка. Значит список обязан совпадать с карточкой на каждом шаге.
- ELO уплывает после каждой записи, поэтому порядок заморозки из шага 1 для ввода не годится. После получения всех N вердиктов от судей просимулируй траекторию: стартуя с текущих `elo/games` из `generate_index()`, жадно выбирай из остатка пачки пару с минимальным `(tier, elo_diff)` (правила те же, что в `get_recommendations`: `tier` по `min_games`: 0 → 0, <3 → 1, иначе 2; `pair_games` внутри пачки у всех 0), применяй предсказанного победителя через `expected_score/k_factor/update_elo` из `tools/elo.py`, повторяй. Это предсказанный порядок карточки (сходится, если предсказанные победители верны).
- Выдай пронумерованный список строго в симулированном порядке: `N. TASK | <idA> vs <idB> → <a|b|draw> (счёт)`. Без ссылок.
- Поясни соответствие id→name один раз при неоднозначности (пример: `devin-gpt-6-astra-max-2` = `Devin GPT-6 Astra Low` в UI): искать ничего не надо, жать «Прогнать» по порядку.
- Если на каком-то шаге карточка показала другую пару (предсказанный победитель не сошёлся) — СТОП, сообщи и пересчитай остаток, не выдумывай ввод.

## Шаг 5. Проверка закрытия и запреты

- После ввода проверь по `load_matchups()`: каждая пара пачки имеет вердикт, победители совпали. Нехватку назови одной строкой (`MISS <a> vs <b>`).
- Не записывай вердикты (ни через UI, ни `record_verdict.py`), не коммить без явной просьбы.
- После закрытия пачки (все N введены) предложи следующую: «пачка закрыта — даю следующие N».

## Формат выдачи

```
1. T-001 | <idA> vs <idB> → **<a|b|draw>** (XX:YY)
...
Пропущены (нет файлов): <idA> vs <idB> — нет файла стороны <A|B|обе>
Аудит: mismatch=N (список), дрейф имён: <что переименовано>
Пачка стартует с позиции UI K
```

## Правила

- Независимость судей как в `benchmark-judge`; анонимность слотов A/B; каждый судит с нуля.
- Вывод — plain-список для кнопки «Прогнать», без ссылок и без ручных dropdown-поисков.
- Кратко, по-русски; код и ID — на английском.
